## 3.1 数据库基础

> 本节解决：数据库分哪两大类？关系型如何用表组织数据、如何保证可靠与加速查询；NoSQL 如何按数据模型分类。

数据库按数据模型分为两大类：**关系型数据库**与**非关系型数据库（NoSQL）**。

### 关系数据库

关系数据库用表组织数据，表由行和列构成，用 SQL 操作，是数据库的两大类之一。

- 主键唯一标识表中的记录
- 外键等关联字段用于建立表之间的关系
- 订单表通过 customer_id 关联客户表，体现表与表之间的关联关系
- DBMS 提供数据定义、查询、事务等管理能力
- 基本 SQL 操作：SELECT 查询、INSERT 插入、UPDATE 更新、DELETE 删除

关系型数据库有两项核心能力：**事务（可靠性）**与**索引（性能）**，分别解决"不出错"与"查得快"。

#### 1 事务

事务是一组不可分割的操作序列，是关系数据库的可靠性能力。

- **ACID 是事务四项性质的英文首字母缩写**

| 字母 | 全称 | 含义 |
|---|---|---|
| A | Atomicity 原子性 | 操作要么全部成功，要么作为整体失败 |
| C | Consistency 一致性 | 事务前后数据都处于合法状态 |
| I | Isolation 隔离性 | 并发事务互不干扰 |
| D | Durability 持久性 | 提交后数据不丢失 |

- **解决什么问题**：数据库随时可能崩溃、并发操作互相干扰，需要保证"一组操作要么全成、要么全不成"
- 原子性靠日志回滚实现：失败时撤销已执行的操作
- 事务隔离级别包括读未提交、读已提交、可重复读、串行化，隔离级别越高并发性能越低
- 为什么级别越高越慢：高隔离需要加更多锁/快照控制，事务相互等待增多，并发度下降

#### 2 索引

索引是关系数据库的性能优化能力，是另一个独立维度。

- **解决什么问题**：全表扫描逐行比对太慢，索引像书的目录，让查询直接定位数据
- 索引提升特定查询的速度——机制：用 B 树/哈希结构按索引键组织，查找从"全表扫描"降为"树/哈希查找"
- 索引需要额外存储空间
- 索引会增加写入和维护的成本——为什么：每次插入、更新、删除时，除改数据外还要同步更新索引结构
- 建立索引只会加快读取而增加写入维护成本

#### 3 存储结构

> 本节把"数据在磁盘上怎么组织、怎么快速查到、怎么保证不丢"拆成 5 个连环问题：**先认识索引结构（B+ 树）→ 再看存储最小单位（row/page）与落盘位置（表空间/.ibd）→ 接着看是谁实现这套组织（InnoDB）→ 最后看性能（Buffer Pool）与可靠性（redo/undo 日志）**。

**1. B+ 树：用来组织索引、支撑快速查找**

- B+ 树是多路**平衡查找树**，数据库用它给索引建"目录"，让定位从"全表扫描"降到"树查找"
- 为什么用 B+ 树：**层数浅**（多叉、树矮）→ 磁盘 IO 少；**叶子节点之间有链表** → 利于范围查询与排序
- 两类索引（高频）：
  - 主键索引 = **聚簇索引**：叶子节点直接存**整行数据**
  - 普通（二级）索引：叶子只存**主键值**，命中后需**回表**取整行

**2. 存储：最小单位 row / page，落盘到表空间 .ibd**

- **行 Row**：记录按行存放，是最小的逻辑记录
- **页 Page**：InnoDB 读写磁盘的**最小单位**，默认约 16KB，一页放多行；所有行都装进页里
- **表空间 / 数据文件 .ibd**：页最终落到 .ibd 文件；默认一张表一个 .ibd（独立表空间），位于库目录 `库名/表名.ibd`
- .ibd 里装的**不只有数据行，还有索引（B+ 树）**——数据和索引一起落盘

**3. InnoDB**

- InnoDB 是 **MySQL 的默认存储引擎**，支持**事务（ACID）、行级锁、外键**
- 它负责把数据按**表空间**组织、落盘到 **.ibd** 数据文件（不同存储引擎的数据文件格式不同）

**4. Buffer Pool**

- **内存缓冲池（数据页缓存区）**：把热点数据页缓存到内存，**减少磁盘 IO**
- 作用：查询先看内存，命中直接返回、避免每次读磁盘——是"查得快"的关键

**5. redo / undo 日志"**

- **可靠性靠两套日志 + WAL（先写日志再落盘）**：
  - **redo**：崩溃后**重做**已提交的数据（恢复，防丢）
  - **undo**：失败时**回滚**未完成的操作（撤销，保原子性）
- 注意：redo/undo 是**独立的日志文件，不在 .ibd 里**——.ibd 存数据与索引，日志负责恢复与回滚，二者职责不同

### NoSQL 数据库

NoSQL 不是 SQL 的一种，而是与关系数据库**并列**的非关系型数据库类别，按数据模型分类，与存储介质无关，不使用 SQL 作为统一标准：

| 类型 | 数据组织 | 底层存储结构 | 适合场景 |
|---|---|---|---|
| 键值 | 键值对 | 内存哈希表，有序集合用跳表 | 按唯一键快速读写简单状态 |
| 文档 | JSON 文档 | BSON 二进制，B 树 / LSM 树 | 灵活结构、嵌套数据 |
| 宽列族 | 列族组织 | LSM 树（写先进内存再批量刷盘） | 海量稀疏、按列族组织的数据 |
| 图 | 节点与边 | 邻接结构直接存 | 关系网络查询 |

### 与关系型对比
关系型 强在“事务（ACID）+灵活查询”：
1. 强于事务（ACID）
    关系型能保证"一组操作要么全成、要么全不成"，数据可靠。
    场景：银行转账、订单扣款、库存扣减——钱不能多转少转，必须 ACID。

2. 强于灵活查询
    SQL 能做复杂查询：多表 JOIN 关联、聚合（GROUP BY）、子查询、任意条件组合。
    场景：财务报表"按部门、按月份汇总多个表"——关系型一条 SQL 搞定。

NoSQL 强在“海量+高并发+灵活结构”：
1. 强于海量：容易横向扩展（多台机器分片），撑得起海量数据；关系型分库分表复杂。

2. 强于高并发：键值/文档读写极快、延迟低。场景：商品页缓存、登录会话、热点数据——Redis 这类按键直取，QPS 远高于关系型。

3. 强于灵活结构：字段可变、可嵌套，改结构不用改表。场景：用户资料（不同用户字段不同）、JSON 文档——关系型要 ALTER TABLE 改表结构，NoSQL 直接存。

 衔接：数据库是"重量级"存储；轻量数据用文件加 JSON 即可——下一节讲数据文件与 JSON。

### 数据文件与 JSON

> 本节解决：不依赖数据库时，如何用文件保存与读写数据，与数据库如何取舍。

- JSON 是轻量级数据交换格式，以键值对和嵌套结构组织数据
- JSON 适合保存结构化数据，例如学生信息、配置项
- 程序启动时从数据文件加载数据，写入时保存到文件，实现持久化
- 数据持久化保证程序重启后数据不丢失
- 数据处理流程：读取文件、解析、更新、写回文件
- 统计类结果从数据实时计算得出，写死在程序中的固定结果无法反映数据变化
- 与数据库的取舍：数据量小、结构简单用文件 + JSON（零依赖、易读易改），量大、高并发、要事务时用数据库

单机存好数据后，系统之间如何协作——下一节讲中间件。

## 3.2 中间件

> 本节解决：系统间如何通过通用能力协作，消息如何异步传递与可靠处理。

### 中间件的定位与能力

中间件位于操作系统基础能力与业务应用之间，为分布式应用提供通用能力。

- 通用能力包括事务协调、通信、消息传递、服务治理
- 中间件减少应用重复实现，促进系统集成；企业把认证、消息事务等通用能力集中到中间件层，避免每个应用各自实现
- 为什么需要中间件：若每个应用各自实现通信与事务，重复且难统一，集中到中间件层可复用与统一治理

中间件按能力分为多个子类：

| 子类 | 通用能力 | 代表产品 |
|---|---|---|
| 消息中间件 | 异步消息传递、削峰解耦 | Kafka、RabbitMQ |
| 缓存中间件 | 高频读加速 | Redis |
| 分布式协调 | 配置、锁、选举 | ZooKeeper |
| 事务协调 / 服务治理 | 分布式事务、服务治理 | 注册中心、分布式事务中间件 |

### 消息队列

消息队列通过生产者、队列或主题、消费者实现异步与解耦。

- 生产者发送消息，消费者按自身能力处理
- 高峰期请求短时间激增时，消息队列先承接再按消费者能力处理，实现削峰缓冲
- 异步处理让生产和消费解耦，不互相阻塞

消息可靠处理需要以下机制配合：

- 确认机制，消费者处理成功后才确认，避免失败被当作成功
- 失败重试，处理失败的消息重新投递
- 幂等处理，重复消费同一消息不会产生重复业务
*幂等：同一个操作执行一次和执行多次，产生的结果完全一样
- 死信或异常消息处理，超过重试次数的消息转入专门队列

- 代表产品：Kafka 面向高吞吐日志和流处理，RabbitMQ 面向灵活路由和低延迟

### 缓存中间件

缓存中间件把热点数据放到内存，加速读取、降低数据源压力。

- **解决什么问题**：每次请求都查数据库太慢且扛不住高并发，热点数据放内存可毫秒级返回
- 机制：读请求先查缓存，命中直接返回；未命中再查数据源并回填缓存
- 场景：商品页、登录会话、排行榜、验证码等高频读数据
- 注意：缓存与数据源需保证一致性；缓存失效瞬间大量请求同时回源（缓存击穿/雪崩）要有应对
- 代表产品：Redis 内存键值存储，用于缓存和会话

### 分布式协调

分布式协调为集群多节点提供配置、锁与选举等一致性能力。

- **解决什么问题**：多个节点需要"谁当主、共享配置、避免并发冲突"，缺乏统一协调会各自为政
- 机制：提供分布式锁、配置中心、服务注册发现、Leader 选举
- 场景：集群选主、多实例共享配置、分布式任务不重复执行
- 代表产品：ZooKeeper 等提供配置与协调能力

### 事务协调与服务治理

- **事务协调**：跨应用、跨库的操作要保证一致性（分布式事务），由事务协调中间件统一协调提交与回滚
- **服务治理**：微服务互相调用，需要服务注册与发现、负载均衡、限流、熔断等治理能力
- 场景：订单服务调用支付、库存服务；大规模微服务集群管理
- 代表产品：服务注册中心（如 Nacos、Consul）、分布式事务中间件


## 3.3 虚拟机与容器

> 本节解决：应用如何打包部署，容器与虚拟机的取舍，容器如何服务智能体与推理。

### 虚拟化

虚拟化的目标：把一台物理机的资源抽象成多台"逻辑机"，提高资源利用率与隔离性。主流有两种方式：

#### **虚拟机**

通过 Hypervisor 模拟完整硬件，每个虚拟机包含独立操作系统。

- Hypervisor（虚拟机监控器，VMM）是运行在物理硬件与虚拟机之间的一层软件，负责把一台物理机的 CPU、内存、磁盘、网络等资源抽象、切分、调度给多台虚拟机，让它们各自以为"独占"一台机器。
- Hypervisor 分两类：Type1 裸金属（KVM、VMware ESXi）直接运行在硬件上，性能好；Type2 寄居（VirtualBox、VMware Workstation）运行在宿主操作系统之上
- 开销大：每台虚拟机都要启动并维护一个完整内核与操作系统，内存、CPU、磁盘都重复占用

#### **容器**

共享宿主机内核，只打包应用及依赖。

- **隔离机制**：命名空间 Namespace 让每个容器有独立的进程、网络、挂载等视图；控制组 cgroup 限制 CPU、内存等资源用量
- 启动快：容器直接运行进程，无需启动整个操作系统
- **镜像分层**：镜像由多层只读层堆叠、运行时加一层可写层（UnionFS 联合文件系统），层可复用，镜像更小、构建更快
- 容器适合微服务和批量部署，虚拟机适合强隔离场景
- Docker 是主流容器工具，镜像包含应用和运行环境，镜像构建后可在任意 Docker 环境运行——实现环境一致性

### 容器镜像与实例

- **镜像**：静态模板，由只读层组成，用 Dockerfile 构建，可拉取复用
- **容器**：镜像运行后的实例，拥有独立的可写层
- 关系：一个镜像可启动多个容器实例；运行时的改动写进可写层，不影响镜像本身
- 容器网络和存储卷提供对外访问与数据持久化

### 容器基础命令：构建与运行全流程

**① 写 Dockerfile**（定义镜像内容）

```dockerfile
FROM python:3.11-slim        # 基础镜像
WORKDIR /app                 # 工作目录
COPY requirements.txt .      # 先复制依赖清单
RUN pip install -r requirements.txt   # 安装依赖（层缓存，改得少重建快）
COPY app.py .                # 复制应用代码
EXPOSE 8000                  # 声明对外端口
CMD ["python", "app.py"]     # 容器启动命令
```

**② 构建镜像**

```bash
docker build -t myapp:v1 .   # -t 打标签(名称:版本)；. 用当前目录的 Dockerfile
docker images                # 查看本地镜像
```

**③ 运行容器**

```bash
docker run -d -p 8000:8000 --name myapp myapp:v1
# -d 后台运行；-p 宿主机端口:容器端口；--name 容器名
docker ps                    # 查看运行中容器
docker ps -a                 # 查看所有容器（含已停止）
```

**④ 进入与调试**

```bash
docker exec -it myapp bash   # 进入容器交互终端
docker logs myapp            # 查看容器日志
docker inspect myapp         # 查看容器详情
```

**⑤ 停止与清理**

```bash
docker stop myapp            # 停止容器
docker rm myapp              # 删除容器
docker rmi myapp:v1          # 删除镜像
```

**⑥ 多容器编排**

```yaml
# docker-compose.yml
services:
  web:                      # 第一个服务
    build: .                # 用当前目录的 Dockerfile 构建镜像（自己写的代码）
    ports: ["8000:8000"]    # 宿主机 8000 端口 → 容器 8000 端口（对外可访问）
  redis:                    # 第二个服务
    image: redis            # 直接用现成的 redis 镜像（不用构建）
```

```bash
docker compose up -d      # 按清单构建并启动所有服务（-d 后台）
docker compose ps         # 查看整套服务的状态
docker compose logs -f    # 同时看所有服务的日志
docker compose down       # 一起停止并移除
```

- 完整闭环：写 Dockerfile → build 构建镜像 → run 启动容器 → exec/logs 验证 → stop/rm 清理
- 现成镜像可直接 docker pull 拉取，自建镜像可用 docker push 上传仓库

### 容器与智能体环境

- 智能体运行环境可用容器打包，保证依赖一致
- 模型推理服务常以容器方式部署，便于迁移和扩缩容
- 容器环境与宿主机隔离，访问宿主机资源需要显式挂载和权限配置


### 虚拟机与容器对比

| 维度 | 虚拟机 | 容器 |
|---|---|---|
| 隔离级别 | 整机级（独立操作系统） | 进程级（共享宿主机内核） |
| 启动速度 | 慢（需启动 OS） | 快（直接起进程） |
| 资源占用 | 大（每台一份 OS） | 小（共享内核） |
| 安全性 | 强隔离 | 较弱（内核共享，有逃逸风险） |
| 可移植性 | 依赖 Hypervisor | 镜像跨环境一致 |

单机部署讲完，多机如何协同——下一节讲分布式系统基础。

## 3.4 分布式系统基础

> 本节解决：多机协作时，一致性、可用性、容错如何取舍，如何降低单点故障风险。

- **CAP 定理**：分布式系统在 C 一致性、A 可用性、P 网络分区容错性之间需要取舍
- P 网络分区（network partition）：节点之间的通信链路被切断，集群被割裂成几个互不能通信的小团体
- 分区容错性在分布式系统中必须满足，因为网络故障不可避免，系统必须能在分区下继续工作
- 单点故障风险通过冗余和集群方案降低，多副本与集群让单点故障不再拖垮系统

### CP 与 AP 的取舍模式
CP 与 AP 是分布式系统**设计时选定的取舍策略（系统属性）**，不是网络异常时才临时启用的机制；因为分区无法避免（P 必选），系统必须预先决定保一致性（CP）还是保可用性（AP）。

**三个时段下 CP / AP 的操作**：

**① 网络正常时**：

- CP：写请求**同步确认**——必须同步到多数副本，半数副本确认后才返回成功，所有副本实时一致
- AP：写请求**异步复制**——本节点立即写入并返回成功，后台再复制给其他副本，最终一致
- 共同点：最终数据都一致；区别只在"确认时机"——CP 等多数副本、AP 立即

**② 分区时**：

- CP：含"多数"的团体继续服务（多数派是权威），达不到多数的团体拒绝请求——宁可不可用，也不给错数据
- AP：两个团体各自继续服务、各自独立写——可用性保住，但数据暂时不一致
- 多数 / 少数的意义：分区时 CP 靠多数派判断谁是权威，少数团体被拒

**③ 网络恢复后**：

- CP：补同步分区期间积压的差异，少数团体重新并入多数阵营；因被拒期间没有新写入，补起来简单
- AP：收敛——交换分区期间各自的写操作、按版本合并（LWW 最后写入胜出、读取修复、反熵、CRDT），最终一致；不可合并的数据可能丢更新

**三时段对照表**：

| 时段 | CP | AP |
|---|---|---|
| 网络正常 | 同步确认（等多数） | 异步复制（立即返回） |
| 分区时 | 多数团体服务、少数拒绝 | 两边都服务，暂不一致 |
| 恢复后 | 补同步积压差异 | 冲突合并收敛（最终一致） |

**适用场景与代表**：

- CP 适合：银行转账、配置中心、分布式锁，数据绝不能错——ZooKeeper、HBase、etcd
- AP 适合：点赞、购物车、会话缓存，可用性优先、稍旧也能接受——Cassandra、CouchDB、部分 Redis 集群

**节点 Node**
参与协作的独立计算单元，通常对应一台机器、虚拟机或容器实例；一台物理机可承载多个节点


## 3.5 兼容与迁移验证

> 本节解决：把应用/数据库迁移到国产平台时，先用统一的四个关注点做顶层检查，再按具体场景（业务栈 / 应用 / 数据库）走对应的验证流程。

### 迁移适配的统一方法：四个关注点

无论迁移应用、数据库还是整套系统，跨架构/跨平台的兼容检查都落在**四个通用关注点**上：

| 关注点 | 检查什么 |
|---|---|
| 1 工具链 | 源代码能否按目标架构编译 |
| 2 二进制依赖 | 第三方库是否有对应架构版本 |
| 3 外设驱动 | 显卡、网卡、声卡、USB 等是否稳定 |
| 4 性能验证 | 关键业务是否达到可用性能 |

- 四层可行性验证：
  - 能不能编出来（工具链）
  - 跑起来缺不缺库（二进制依赖）
  - 接不接得上硬件（外设驱动） 
  - 到底够不够快（性能）

### 具体迁移
#### 业务栈兼容验证

- 兼容验证应针对实际组合后的完整技术栈和相关业务路径
- 完整业务栈包括操作系统、数据库、中间件和应用
- 只验证某个单品能否启动不足以证明整套系统兼容，应用能启动并不能认定各组件之间不存在兼容性问题

#### 应用迁移流程

1. 盘点应用清单与依赖，识别迁移范围、依赖和潜在问题
2. 完成目标架构搭建
3. 功能验证
4. 兼容性验证
5. 回归测试

- 回归测试用于确认迁移没有破坏既有相关功能
- 新系统上线前执行回归测试是标准环节
- 跨架构迁移涉及编译、运行库和驱动等层面的兼容性检查（详见第 5 章 5.2 兼容性层次）
- 其中第 4 步"兼容性验证"，正是把上方四个关注点（工具链 / 二进制依赖 / 外设驱动 / 性能验证）逐一落到应用这个对象上

#### 数据库迁移

- 数据库迁移不能只比较数据条数，需要检查结构、SQL 兼容、数据一致性和关键业务功能，必要时评估性能与高可用方案


## 3.6 国产基础软件生态

> 本节解决：信创环境下国产软件覆盖哪些层、如何构成完整生态。

信创环境下国产软件覆盖基础软件各层：

- 国产数据库：达梦数据库、人大金仓、GaussDB、openGauss、OceanBase
- 国产中间件：东方通中间件、金蝶天燕、宝兰德
- 国产办公软件：金山 WPS、永中 Office
- 国产操作系统：统信 UOS、麒麟系统
- 国产浏览器：360 安全浏览器等基于 Chromium 内核的国产浏览器

- 国产软件与 X86、ARM 等多种架构适配
- 国产数据库大多兼容主流 SQL 标准，支持事务和索引等基础能力
- 中间件提供消息、事务、服务治理等通用能力，应用通过标准接口接入
- 信创环境强调软硬件全栈自主可控，从芯片、操作系统到应用软件形成完整生态
