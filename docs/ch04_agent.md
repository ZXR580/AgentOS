# 第 4 章 智能体技术基础

考核占比 20%。

## 4.1 模型生成文本与智能体执行任务

大语言模型是一个文本生成器，输入 Token 序列，输出 Token 序列。它无法直接操作文件、执行命令或控制软件，文件读写、进程管理、网络请求这些实际动作都发生在模型之外。

- LLM 在 Agent 中负责理解自然语言目标、任务拆解、决策、工具选择和参数生成
- 工具的实际执行由外部执行层完成，执行层按模型给出的参数调用系统能力
- 真正的系统操作需要工具、运行时和操作系统共同完成
- 具备完整 Agent 能力意味着能围绕目标理解、决策和行动，并随环境反馈调整
- 仅包含聊天界面的程序只完成对话，具备完整 Agent 能力
- 固定脚本的执行路径由预设规则决定，Agent 根据执行结果动态调整路径

## 4.2 Agent 架构与闭环

典型 Agent 由五个环节构成：感知接收输入和环境信息，推理与规划拆解任务制定步骤，行动调用工具或执行操作，反思检查结果修正策略，记忆保存历史信息供后续决策使用。

- 五环节共同形成面向目标的执行系统

执行过程形成闭环，顺序为目标、计划、行动、观察、判断：

- 目标描述要完成的任务
- 计划把目标拆成可执行的步骤
- 行动调用工具执行操作
- 观察读取工具或环境的返回结果
- 判断依据结果决定继续、调整或结束

- 工具或环境返回结果必须进入下一步决策，否则错误容易累积而无法及时纠正
- 观察步骤的输入来自环境或工具执行后的实际结果
- 已执行步骤、任务完成条件、当前目标和工具返回结果都会影响下一步动作

## 4.3 Planning 规划

Planning 是任务执行前的拆解环节。复杂目标被拆成可验证的子任务，每个子任务有明确的完成条件，便于逐步验证和推进。

- 任务拆解让复杂目标转化为更容易验证的子任务
- 计划在生成后保持可变更，随执行结果和新信息动态调整
- 执行中发现前置条件不成立时，根据新信息调整计划或重新规划
- 规划时保证所有子任务并行完成，规划的核心是把目标分解到位

## 4.4 工具调用

工具调用让 Agent 获得执行能力。模型依据工具描述选择工具并生成调用参数，外部执行层负责真正调用。

- 工具描述和 schema 声明工具的用途、参数名称、参数类型和取值范围
- 模型依据清晰的工具描述选择工具并生成参数
- 生成后的参数需要校验类型和取值范围，防止非法参数进入执行层
- 工具描述明确何时使用和不能做什么，降低错误工具选择和越权调用
- 工具调用失败时分析失败原因，决定重试、换工具或终止
- 有副作用的操作避免无条件重试，重复执行可能造成重复业务
- 工具返回错误信息时默认成功或直接忽略错误

## 4.5 记忆

记忆模块保存后续决策可能需要的历史信息。对话中的临时信息放在短期记忆中，随上下文窗口轮换；需要长期保留的信息写入外部持久化存储，形成长期记忆。

- 长期记忆可跨会话使用，保存范围大于有限的上下文窗口
- 长期记忆设计需考虑哪些信息值得保存、信息是否过期、谁有授权访问、检索时如何控制相关性
- 长期记忆检索出过期信息时，为记忆增加时间来源或有效性判断
- 记忆写入与检索都要有访问控制

## 4.6 RAG 与向量检索

RAG 检索增强生成解决模型知识有限的问题。模型训练数据有截止日期，内部制度、最新文档等知识模型并不掌握，RAG 把外部知识在生成前注入上下文。

完整流程：

1. 文档切块，把长文档拆成适合检索的文本片段
2. 用 Embedding 模型把片段编码为向量，存入向量库
3. 用户提问时把问题编码为向量，在向量库中检索相似片段
4. 把检索结果拼入 Prompt 上下文，交给模型生成回答

- Embedding 把文本映射到向量空间，语义相近的文本向量距离更近
- 向量相似度衡量当前表示下的语义接近程度
- 高向量相似度说明两个文本在当前表示中更接近，单独不能证明事实内容一致
- RAG 在推理时检索外部知识并加入上下文，为新增知识无需修改基础模型参数，与微调不同
- Agent 型 RAG 把检索作为主动能力，根据当前情况决定是否再次检索、换查询或取消检索

知识库构建的质量决定检索效果：

- 切块大小影响检索粒度，块太小语义不完整，块太大命中不精准，常用几百到上千 Token 的块
- 切块可设置重叠，相邻块共享边界内容，防止语义被切断
- 检索后可用重排 Rerank 对候选结果二次排序，提升答案质量
- 混合检索结合向量相似度与关键词匹配，兼顾语义和精确词命中
- 知识库需定期更新，新增文档重新切块并写入向量库
- 检索相关性可通过查询改写提升，例如把口语化问题改写为规范表述

## 4.7 MCP

MCP 模型上下文协议为 AI 工具调用制定统一标准。每个工具厂商只需实现一次协议，所有支持 MCP 的 AI 应用都能使用。

- Server 负责暴露和提供 Tool，把工具能力标准化
- Client 负责连接 Server，发起工具调用请求
- 统一协议减少不同 AI 应用重复适配外部能力的成本
- MCP 类比为 AI 界的 USB，一次开发即可被所有支持 MCP 的 AI 使用
- 工具数量较多时 MCP 的价值明显，工具较少时直接调用 API 更简单

MCP 服务开发要点：

- 服务启动时向客户端声明工具清单，每个工具包含名称、描述和参数定义
- 工具参数以 schema 形式定义，名称、类型、必填项清晰声明
- 工具处理异常输入时应返回明确结果，导致服务进程退出
- 工具内部的数据需要持久化时写入本地文件，服务重启后重新加载
- 数据文件常用 JSON 格式，读写方便且结构清晰
- 服务接入客户端后在配置中注册，客户端重启后重新发现工具
- 完成接入后实际调用工具验证功能，并测试服务重启后的数据完整性

## 4.8 Skill

Skill 是 Agent 预定义的专业能力模块，把一组工具和业务流程封装成可复用的高层能力。

- Skill 的抽象层级高于单个底层 Tool
- 一个 Skill 可以调用多个底层工具，组合成完整方案
- Skill 封装领域专家的工作流程，用户直接下达目标即可使用
- 大部分 Skill 本质是封装好的函数调用，智能来自工具的选择和组合

## 4.9 CoT

CoT（Chain-of-Thought，思维链）是引导模型"先逐步推理、再给出答案"的提示技术，能显著提升数学、逻辑、常识推理类问题的表现。

- 大模型直接回答复杂问题时容易"跳步出错"，把推理过程显式写出来可降低错误率
- CoT 的核心：在 Prompt 中要求模型输出中间推理步骤，再给出最终答案
- 让模型"一步一步想"相当于给模型更多中间计算状态，减少粗心错误与幻觉

常用形式：

- Few-shot CoT：在示例中展示"推理步骤 + 答案"的完整过程，让模型模仿
- Zero-shot CoT：不给示例，只加一句"Let's think step by step"（让我们一步一步地思考）即可触发分步推理
- CoT-SC（Self-Consistency，自洽性）：同一问题让模型多次独立推理，对多个答案投票取多数，进一步提升正确率

适用与局限：

- 适合需要多步计算的数学题、需要链条式推理的逻辑题、需要逐步拆解的规划类任务
- 不适合简单事实问答（直接回答更快、更省 Token）
- 推理步骤本身也可能出错，CoT 只是降低出错概率，并不保证正确
- 与 ReAct 的区别：CoT 的"思考"不一定会触发外部工具调用，ReAct 把思考与工具行动交织在一起（详见 4.15）

## 4.10 Transformer

大语言模型（LLM）基于 Transformer 架构。理解它有助于理解 Agent 的上下文窗口、Token、注意力等概念。

### 核心思想：注意力机制

- 注意力（Attention）让模型在处理一个词时，能"关注"输入序列中所有其他词，并加权融合它们的信息
- 相比早期 RNN 逐词串行处理，Transformer 可并行处理整段序列，训练更快、能捕获长距离依赖
- 自注意力（Self-Attention）中，每个词都会计算与序列中其他词的关联权重（Query/Key/Value 三组向量）

### 多头注意力与位置编码

- 多头注意力（Multi-Head Attention）：并行多组注意力头，分别关注不同的语义关系（语法、指代、主题等），再拼接融合
- 位置编码（Positional Encoding）：注意力本身不区分词的先后顺序，需注入位置信息，模型才能理解"第几个词"
- 层归一化、残差连接、前馈网络（FFN）共同构成 Transformer 的基本块

### 架构形态与 LLM

- 原始 Transformer 是 Encoder-Decoder（编码器-解码器）结构
- 主流 LLM（如 GPT 系列）采用 **Decoder-only**（仅解码器）结构：只保留解码器，用"预测下一个 Token"的方式训练与生成
- LLM 生成过程是逐 Token 自回归：根据已生成的前文预测下一个 Token，反复迭代直到结束

### 训练三阶段

1. 预训练（Pre-training）：在大规模无标注语料上学习"预测下一个 Token"，得到语言能力基础
2. 指令微调（SFT）：用"指令-回答"数据对齐，让模型学会听从指令
3. 人类反馈强化学习（RLHF）：让模型输出更符合人类偏好与安全要求

### 与 Agent 相关的关键概念

- Token：模型处理文本的最小单元（常为子词），中文一个字可能拆成多个 Token；上下文窗口以 Token 计
- 上下文窗口：模型一次能处理的 Token 上限，超出部分会被截断或需压缩，直接影响 Agent 的记忆容量
- KV Cache：推理时缓存已计算的 Key/Value 以加速生成，是显存占用的大头
- Embedding 与 Attention 是 RAG 与向量检索的底层原理（见 4.6）

## 4.11 智能体开发框架（LangChain / ReAct / Function Calling）

从零手写 Agent 可行，但生产级 Agent 通常基于成熟框架开发，以复用工具集成、记忆、编排与部署能力。

### 主流框架对比

| 框架 | 定位 | 特点 |
|---|---|---|
| LangChain | LLM 应用开发框架 | 提供模型、Prompt、工具、记忆等可组合组件，生态庞大 |
| LangGraph | Agent 编排框架（官方） | 用图结构管理状态与流程，支持循环、分支、持久化，适合复杂有状态 Agent |
| Dify | 可视化低代码平台 | 拖拽搭建工作流与 Agent，适合快速交付与团队协作 |
| AutoGen / AG2 | 多智能体框架 | 侧重多 Agent 对话协作 |

### LangChain 核心组件

- Models：统一接口封装各类大模型（OpenAI、国产模型等），可随时切换
- Prompts：Prompt 模板与示例管理
- Tools：封装函数 / API 为工具，供 Agent 调用
- Memory：对话与长期记忆管理
- Chains / Agents：串联组件形成执行流程；Agents 支持动态决策

### LangGraph 与真实项目

- LangGraph 以"节点 + 边 + 状态"定义 Agent 流程，天然支持 ReAct 式的循环（思考-行动-观察）、条件分支与人工介入
- 官方提供 LangGraph 内置 ReAct 实现，是构建复杂 Agent 的主流选择

### ReAct 与 Function Calling

- ReAct：推理与行动交织，循环为"思考→行动→观察→再思考"，直到信息充足输出答案（详见 4.15）
- Function Calling（函数调用）：模型输出结构化的调用请求（函数名 + JSON 参数），外部执行层真正执行并把结果回传模型；OpenAI 兼容接口与多数框架均支持
- 两者关系：ReAct 是 Agent 的组织模式，Function Calling 是模型与工具之间的调用协议；现代 Agent 常用"ReAct 模式 + Function Calling 协议"组合实现

## 4.12 多智能体协作

多 Agent 系统让多个专业 Agent 分工协作，例如研究、写作、审核分别由不同 Agent 承担，各角色专注自身领域。

- 角色分工和专业化提升整体能力
- 协作引入通信、重复工作和冲突开销
- 增加 Agent 数量并提高任务质量，协调成本随数量增长
- 协调机制包括共享必要状态、明确角色职责、结果汇总或仲裁、任务分配
- 典型流程为研究、编码、审查、测试，反馈修改后交付

## 4.13 安全

Agent 能执行实际操作，安全控制随之而来。主要风险包括提示注入、越权工具调用和不可逆操作。

- 提示注入可能来自用户直接输入，也可能隐藏在网页、文档等外部内容中，外部内容携带的指令同样有效
- 高风险动作前加入人工确认，在不可逆或敏感操作前增加控制点
- 最小权限原则，Agent 只获得任务所需的最小能力
- 可审计工具接口记录操作过程，便于追溯
- 关闭不需要的网络服务可减少系统攻击面

## 4.14 评测指标

工具型 Agent 的评测从多个维度进行：

- 任务成功率，任务是否按预期完成
- 工具选择准确率，是否选对了工具
- 平均调用次数或成本，执行是否高效
- 安全违规率，是否触发了越权或危险操作
- 执行稳定性，多次执行结果是否一致
- 答案正确但调用大量无关工具，说明执行效率和工具选择质量仍需优化

## 4.15 ReAct

ReAct 把推理和行动交织进行，循环流程为思考、行动、观察，再进入下一轮思考，直到任务完成。

- 思考确定下一步做什么，例如搜索什么资料
- 行动调用工具，例如执行搜索
- 观察读取工具返回的结果，例如找到几篇文章
- Observation 承接行动后的外部结果，用于指导后续推理和行动
- 信息充足后停止循环，输出最终结果

## 4.16 工作流与 Agent 框架

- Workflow 是固定流程编排，执行路径预设，适合确定性任务
- Agent 是动态决策，根据执行结果调整路径，适合开放任务
- 工具数量少时直接调用 API 更简单，工具数量多时使用统一协议更高效
- 常见开发框架：LangChain 提供工具链和编排能力，LangGraph 以图结构管理状态流转，Dify 提供可视化应用搭建
- Function Calling 协议：模型输出结构化的函数调用请求，包含函数名和参数，外部执行层调用函数并把结果回传模型
- 工具 Schema 以 JSON 形式描述参数名称、类型和取值范围，模型据此生成合法参数

## 4.17 Agent 评测方法

- 自动评测：比对最终答案，检查工具调用序列是否合理
- 人工评测：评估任务完成度、过程合理性、交互体验
- 自动评估还可检查越权调用和安全违规
- 评测需要覆盖不同难度的任务集合，保证结果稳定

## 4.18 智能体调用系统能力

- 智能体调用操作系统能力通过工具完成，文件读写、命令执行、服务管理封装为工具
- 大模型本身无法直接操作文件或执行命令，工具、运行时和操作系统共同完成实际动作
- 本地 Agent 在受控边界内使用本地数据和工具
- 最小权限、明确接口和审计记录降低自动化执行风险

## 4.19 核心概念速览

- 模型生成文本，Agent 执行任务
- 闭环是 Agent 的运转方式，观察结果驱动下一步决策
- 工具让 Agent 获得执行能力，Schema 保证参数正确
- RAG 补充知识，MCP 统一工具接口，Skill 封装专业流程，Multi-Agent 分工协作

## 4.20 Prompt 工程

Prompt 是发给模型的指令，Prompt 质量直接影响生成结果。

### Prompt 的构成

- 系统提示词设定角色和行为规则，定义模型的整体行为
- 用户提示词是具体任务指令，说明要完成什么、以什么格式输出
- 示例可放在提示词中示范期望的输出形式
- 提示词中的指令要明确、具体，避免模糊表述

### 常用技术

- Few-shot 少样本提示：在提示词中给出若干输入输出示例，让模型模仿示例完成新任务
- 思维链 CoT：引导模型分步推理再给出答案，适合数学和逻辑问题
- 输出格式化：要求模型以 JSON 等结构化格式输出，便于程序解析
- 角色设定：为模型指定专家角色，约束回答风格和范围
- 温度参数影响输出的随机性，低温度适合确定性任务，高温度适合创意生成

### 注意事项

- 提示词中的内容都可能被模型当作指令，用户输入和外部内容需要做注入防护
- 外部检索内容注入提示词前，应与系统指令做隔离
- 复杂任务在提示词中说明执行步骤，降低模型遗漏环节的概率

## 4.21 智能体调试与故障排查

Agent 运行中的常见故障和排查方向：

- 工具调用失败：检查工具描述与 Schema 是否准确，参数是否合法，工具是否可用
- 模型输出乱答：检查 Prompt 是否清晰，检索结果是否注入正确，采样参数是否合理
- 上下文溢出：单次对话内容超过上下文窗口，需要压缩历史或清理无关内容
- 死循环：Agent 反复执行相同动作，需要设置最大迭代次数和 Token 预算限制
- 检索不到答案：检查知识库内容是否覆盖、切块与检索参数是否合理
- 幻觉输出：检索结果与回答不对应，需要约束模型只基于检索内容回答

- 日志记录每一步的思考、工具调用和结果，是定位故障的主要手段
- 调试时逐步执行，观察每一步输入输出，定位出错环节
- Agent 进入死循环或浪费 Token 时，设置最大迭代次数和 Token 预算限制
- 故障记录保留时间、操作和结果，有助于复现问题、审计过程和重复试错

## 4.22 模型调用与推理服务

### 调用方式

- API 调用：通过 HTTP 接口向推理服务发送请求，传入模型名、消息和参数，返回生成结果
- 本地调用：加载模型到本地内存，直接调用模型接口生成
- 本地部署与 API 调用的区别在于模型运行位置，调用逻辑一致

### 推理服务

- Ollama 提供简单易用的本地模型部署和 API 接口
- vLLM 提供高性能推理服务，支持高并发和连续批处理
- 推理服务暴露 OpenAI 兼容接口，应用通过标准接口切换不同后端
- 本地模型部署需要考虑显存容量、量化级别和并发请求数
- 模型推理参数包括温度、最大生成长度、Top-p 等，通过请求参数传入

### 应用构建流程

1. 明确任务需求，确定模型选型
2. 部署模型或接入 API
3. 构建知识库，导入文档并建立索引
4. 接入工具和系统能力
5. 设计 Prompt 和 Agent 流程
6. 运行调试，验证任务完成效果
7. 排查错误，优化迭代

### 任务完成效果验证

- 用测试集验证任务正确率，检查工具调用是否合理
- 评估指标包括任务成功率、工具选择准确率、调用成本、安全违规率
- 验证结果不达标时，从 Prompt、检索、工具参数、模型选型逐项排查
