## 4.1 模型生成文本与智能体执行任务

> 本节回答：为什么"会聊天"不等于"会干活"？——认清 LLM 的本质边界，是理解一切 Agent 设计的起点。

**LLM 是文本生成器，不是执行器**

- 大语言模型是一个文本生成器：输入 Token 序列，输出 Token 序列。它无法直接操作文件、执行命令或控制软件；文件读写、进程管理、网络请求这些实际动作都发生在模型之外。真正的系统操作需要工具、运行时和操作系统共同完成——模型只是链条中的"决策者"，不是"执行者"
- 智能体调用操作系统能力也通过工具完成：文件读写、命令执行、服务管理都封装为工具

**Agent 中的分工**

- LLM 在 Agent 中负责理解自然语言目标、任务拆解、决策、工具选择和参数生成（脑力部分）
- 工具的实际执行由外部执行层完成，执行层按模型给出的参数调用系统能力（体力部分）

下一节先弄清大脑本身：LLM 的工作机制如何决定 Agent 的能力上限。

## 4.2 LLM 原理与 Agent 能力边界

> 本节回答：Agent 的大脑（LLM）如何工作？它的机制如何划定 Agent 的能力上限？本节沿"语言如何被表示 → 用什么结构建模 → 怎么训练 → 如何高效推理 → 有什么能力与局限"的主线展开完整机制，并标注每条对 Agent 的意义。

### Token 与分词

**解决什么问题**：模型不能直接处理整段文本，需要先切成最小处理单元。

Token 是文本切分后的最小处理单元。分词器把文本切分为 Token 序列，常用 BPE 字节对编码，从字符开始逐步合并高频共现片段。

- 一个中文词通常对应 1 个 Token；英文单词可能被拆为多个 Token；也存在一个汉字拆成多个 Token 的情况（生僻字）
- Token 序列是模型输入输出的基本单位，上下文窗口以 Token 数量计量——Agent 的记忆容量、API 计费都以 Token 计

**Token 是文本单元，但模型算的是向量——需要把 Token 映射成向量表示。**

### Embedding

- Embedding 把 Token 映射为固定维度的稠密向量，语义相近的词向量距离更近
- 稠密向量把离散符号变成连续数值，才能进入神经网络的矩阵运算
- 文本可编码为向量，用于相似度计算——Embedding 既在模型内部承担输入表示，也单独用于向量检索（后者详见 1.5 节）
- 对 Agent 的意义：Embedding 与 Attention 是 RAG 与向量检索的底层原理（详见 4.10）

**有了向量表示，还需要能并行处理整个序列、并捕获长距离依赖的结构——Transformer。**

### Transformer 架构

**解决什么问题**：早期 RNN 按序列顺序逐词串行处理，训练慢、长距离依赖容易丢失；Transformer 用注意力替代串行递归，可并行处理整段序列、训练更快、能捕获长距离依赖。

> **Transformer = 把输入编码成向量 → 经 N 层"注意力 + 前馈"块逐层读全序列 → 从最后一位向量预测下一个词**，靠自回归逐字生成。

> 下图把**整体执行流程**与**单块内部结构**合成了一张图：外层是自回归生成流程；中间的"重复 N 层块"节点里已直接标出**每块的内部结构**（自注意力 → 残差/层归一 → FFN → 残差/层归一）。分层看：整体（① 结构、② 输入、③ 生成）→ 微观（⑥ 基本块）→ 核心（④ 注意力、⑤ 多头、⑦ 关键设计）。

按「整体 → 输入 → 生成 → 核心 → 块 → 关键设计」拆开看：

**① 整体结构**：Transformer 分 encoder（编码器，理解输入）与 decoder（解码器，生成输出）；GPT 系列只使用解码器（Decoder-only）。

**② 输入处理（两步）**
  - ① 把 Token 映射为向量（Token Embedding）
  - ② 叠加位置编码，把顺序信息注入向量

**③ 生成机制（Decoder-only）**
  - 输入序列经 N 层块后每个位置都产出一个向量 
  - 取**最后一个位置**的向量
  - 经线性层投影到词表维度得到 logits
  - Softmax 归一化为概率分布 
  - 解码：选一个 Token（贪心取最大 / 按温度采样）
  - 追加到序列末尾，整段再前向一次、又取新的"最后一位"

**④ 自注意力** 
  - 每个 Token 向量分别乘三组权重矩阵得 Q（查询，想关注谁）、K（键，供匹配标签）、V（值，被取走内容）
  - 用 Q 与序列所有 K 做点积得分数，除以 √d_k 缩放，Softmax 归一化为权重，再对各 V 加权求和——得到融合全序列信息的输出。
    
     为什么除以 √d_k：点积随维度增大而变大，直接进 Softmax 易落入饱和区导致梯度消失，缩放可稳定梯度。

**⑤ 多头注意力**：把 Q、K、V 投影到多个子空间并行计算，每个头关注不同语义关系（语法、指代、主题等），结果拼接后经线性层输出。（矩阵级 MHA 细节见 1.2）

**两个关键设计**
  - **因果掩码**：自注意力上加掩码，保证生成第 n 个 Token 时只能看到前 n−1 个（看不到未来）
  - **KV Cache**：让每步不必重算前面 Token 的 K/V。


### 位置编码
- 位置编码服务于序列的顺序信息，与磁盘读写等存储操作无关

- 绝对位置编码把位置信息直接加进 Token 向量，例如正弦编码
- 旋转位置编码 RoPE 通过旋转矩阵把相对位置信息编码进注意力计算，外推性好，主流模型广泛使用——因为编码的是"相对位置"而非绝对位置，序列更长时仍可外推到训练长度之外


**结构确定后，用什么任务让模型学会语言？——自回归语言建模，再经历三阶段训练。**

### 自回归生成与训练范式

- 大语言模型采用自回归生成：逐 Token 预测下一个 Token，根据已生成的前文反复迭代直到结束
- 因果语言建模只利用左侧上下文预测当前 Token，与解码器结构一致；掩码语言建模随机遮盖部分 Token 让其重建，BERT 采用
- 预训练阶段在无标注语料上做语言建模，学习通用语言能力

训练三阶段：

1. 预训练：无标注语料自监督训练，学习通用语言能力
2. 微调（SFT）：用带指令或示例的数据训练，让模型学会按指令行事
3. 对齐（RLHF）：通过人类反馈的强化学习，让输出符合人类偏好——对齐确保 LLM 输出有益、无害、诚实

- 训练需要正向传播和反向传播，反向传播逐层计算梯度，计算量远超推理；推理只进行一次正向传播，逐个生成 Token，关注延迟和吞吐量

### 注意力变体与 KV Cache

**解决什么问题**：标准多头注意力 MHA 能力强，但每头独立的 QKV 让计算和 KV 缓存开销随规模急剧膨胀；注意力变体在不明显损失质量的前提下"省 KV、省显存、省计算"。

**KV Cache**——生成逐 Token 进行，每一步计算注意力时需要当前 Token 的 Q 与前面所有 Token 的 K、V 运算：

- KV Cache 把已生成 Token 的 K 和 V 矩阵缓存下来，每步只计算新 Token 的 Q，直接复用缓存的 K、V
- 避免每步重新计算之前所有 Token 的注意力，显著提升推理速度——没有缓存时，第 n 步要重算前 n−1 个 Token 的注意力，计算量随序列二次增长
- KV Cache 随序列长度线性增长，是推理显存占用的重要组成部分
- 对 Agent 的意义：KV Cache 是显存占用的大头，决定本地部署成本（详见 4.18）

**演进主线：MHA → MQA → GQA → MLA（省 KV Cache）**

先把 **MHA 的矩阵级细节**讲清（作为基线）：
- 输入是上一层输出的**隐状态矩阵 $H$**（第 $t$ 个 Token 记 $h_t$，维度 $d$，$T$ 个 Token 堆叠成 $T \times d$）；$h_t$ 由 Token 经 Embedding + 位置编码、再逐层经"注意力 + 残差 + 层归一 + 前馈"更新而来
- 每个注意力头各有一套投影矩阵 $W^Q$/$W^K$/$W^V$，把 $h_t$ 派生成 $q_t$（查询，想关注谁）、$k_t$（键，供匹配的标签）、$v_t$（值，被取走的内容）
- 分数 $s_{ij} = \frac{q_i \cdot k_j}{\sqrt{d_k}}$（除以维度平方根防点积过大落入 softmax 饱和区），Softmax 归一化为权重 α，再对各 $v_j$ 加权求和；多头把该过程并行做 H 次（每头 $d_k=d/H$），各头输出沿特征维拼接后经 $W^O$ 融合回 d 维（$H \times d_k = d$，计算量与单头相当）
- **代价**：每头独立 QKV → KV Cache 和计算量都大——这正是变体要解决的问题

**四种变体对比（列表比较）**：

| 变体 | 机制 | KV Cache | 质量 | 代表 |
|---|---|---|---|---|
| MHA 多头注意力 | 每头独立 QKV，多子空间并行 | 最大（每头一份 K/V） | 最强 | 标准 Transformer、GPT |
| MQA 多查询注意力 | 所有头**共享同一组 K/V** | 最小（一份 K/V） | 损失较大 | 早期高并发推理 |
| GQA 分组查询注意力 | 在**若干头之间共享 KV**（分组） | 中等（折中） | 较稳 | Llama 系列 |
| MLA 多头潜在注意力 | 把每 Token 的 K/V **压成低维潜向量**，缓存只存潜向量、算时再展开 | 大幅缩小（约 93%） | 基本不丢 | DeepSeek |

**MLA 压缩细节（DeepSeek 提出）**：
- 压缩（缓存侧）：$c_t^{KV} = W^{DKV} \cdot h_t$，把 $d$ 维隐状态压成 $d_c$ 维（$d_c$ 远小于所有头 KV 总维度）
- 展开（计算侧）：每个头用上投影 $W^{UK}$、$W^{UV}$ 从 $c_t^{KV}$ 还原出自己的 $k_t$、$v_t$
- 为什么能省缓存：缓存的是低维 $c_t^{KV}$ 而非每头完整 KV；把 $W^{UK} \cdot W^{DKV}$ 合并成一个矩阵后，每步算出的 k、v 与标准 MHA **完全等价**——计算量不变、缓存却大幅变小
- 不损质量原因：KV 权重矩阵**近似低秩**，低维潜向量已能承载绝大部分信息（与 LoRA 同思路）
- 解耦 RoPE：位置信息不能压进共享潜向量，额外用独立"旋转键"通道承载——内容走压缩通道、位置走旋转通道，互不干扰

（FlashAttention 不改结构，靠分块计算把注意力切成小块、减少显存读写，加速注意力运算。）

- 小结：MHA 用"多子空间"换表达能力，MQA/GQA 用"共享"换缓存，MLA 用"低秩压缩"换缓存且基本不丢质量，FlashAttention 用"分块"换速度——主线是"用尽量小的代价保住注意力能力"。

### 上下文窗口

- 上下文窗口限制模型一次推理可直接使用的 Token 数量范围；超出窗口的历史信息无法参与本次生成（GPT-4 为 128K Token，Gemini 可达 1M Token 以上）
- 生成行为受上下文窗口、Prompt 内容、模型能力和采样参数共同影响
- 对 Agent 的意义：窗口直接决定记忆容量与单轮可用信息量（详见 4.9）；窗口内的内容模型"看得见"，窗口外等于不存在——记忆（4.9）与 RAG（4.10）本质都是围绕这条硬约束设计的外挂方案

### 上下文学习、思维链与幻觉

- 上下文学习 ICL 指模型从 Prompt 中的示例学习新任务，无需更新参数
- 思维链 CoT 让模型先输出推理步骤再给出答案，提升复杂推理能力（Agent 视角的形式与适用边界见 4.12）
- 上下文窗口限制可放入的示例和推理过程长度
- 幻觉指模型生成看似合理但事实错误或虚构的内容——幻觉源于模型对知识的模糊记忆和概率采样，模型不是在"查库"，而是按概率续写，记错或没有依据时就编造
- 模型知识有截止日期，训练数据无法覆盖最新信息——这正是 RAG（4.10）要解决的问题

### Scaling Laws（规模法则） 与涌现

- Scaling Laws 表明模型性能随参数量、数据量和计算量增加而可预测地提升，呈幂律关系
- 涌现能力指模型规模超过阈值后突然具备的新能力，例如推理和编程
- 涌现能力是规模法则的重要体现

**两条机制级推论（贯穿全章）**

- 为什么逐 Token 自回归重要：模型没有隐藏的"草稿纸"，"思考"和"输出"是同一机制、边生成边吐出——这正是 CoT（4.12）要求"把思考显式写出来"的根本原因
- 为什么上下文窗口是硬约束：窗口内的内容模型"看得见"，窗口外等于不存在——记忆（4.9）与 RAG（4.10）本质都是围绕这条硬约束设计的外挂方案

零件清单里最重要的零件（大脑）已看清，现在看 Agent 整体由什么组成、如何运转。

## 4.3 Agent 认知架构：结构维与行为维

> 本节回答：认识一台机器，先看零件清单（结构维），再看运转流程（行为维）——Agent 同理。**上位概念是 Agent 认知架构（cognitive architecture）**：它不再只是"零件堆叠"，而是用"由什么组成 + 如何运转"两个正交维度统摄整个 Agent。本节是全章地图。

### 上位概念

- 学界一致把 Agent 抽象为一种**认知架构**，从两个维度分析：
  - **结构维（components，零件/组件）**：Agent 由哪些零件构成——对应 LangGraph 的 **nodes**
  - **行为维（control flow，主循环）**：Agent 如何持续运转——对应 LangGraph 的 **edges / 条件边**

- **"零件清单"（结构）+ "主循环"（行为）= 一个完整 Agent**；一横一纵，是同一架构的两个正交切面，不是同一维度

### 结构维：五环节（组件 / 零件清单）

<Pillars data='{"title":"结构维 · 五环节","pillars":[{"title":"感知","desc":"多通道感知环境与输入"},{"title":"规划","desc":"把目标拆成可验证子任务"},{"title":"行动","desc":"调用工具 / MCP / Skill 执行"},{"title":"反思","desc":"评估结果并修正行为"},{"title":"记忆","desc":"存经历、跨会话复用"}]}' />


典型 Agent 由五个组件构成，共同形成面向目标的执行系统。

- **感知**：接收输入和环境信息
- **推理与规划**：拆解任务、制定步骤
- **行动**：调用工具或执行操作
- **反思**：检查结果、修正策略
- **记忆**：保存历史信息供后续决策使用

### 行为维：执行闭环（主循环 / agentic loop）

主循环各文献叫法略异（perceive-reason-act、agentic loop、ReAct 的 thought-action-observation、Boyd 的 OODA loop），此处统摄为"目标 → 计划 → 行动 → 观察 → 判断"：

- 目标：描述要完成的任务
- 计划：把目标拆成可执行的步骤
- 行动：调用工具执行操作
- 观察：读取工具或环境的返回结果
- 判断：依据结果决定继续、调整或结束


### 两维对应关系（高频考点）

结构维与行为维一个讲"组成"、一个讲"运转"，是同一认知架构的两个正交视角：

| 闭环步骤（行为维） | 对应五环节（结构维） | 说明 |
|---|---|---|
| 目标 | 感知 | 接收并理解任务 |
| 计划 | 规划 | 拆解步骤 |
| 行动 | 行动 | 调用工具 |
| 观察 | 感知（读反馈） | 输入来自环境 / 工具实际结果 |
| 判断 | 规划 + 反思 | 决定继续、调整或结束 |
| （贯穿全程） | 记忆 | 属五环节但不在主循环序列，每步决策都可能读历史、写历史 |

- 结构维是"零件清单"，行为维是"主循环"；缺任一环节闭环就跑不完整（如没有观察就没有反馈，错误会累积）

**感知的深化：多通道输入**

"感知：接收输入和环境信息"不止文本——Agent 的输入通道越多，越能理解真实环境：

- 用户输入通道：文本、语音（语音接口）、图像/视觉（视觉接口）
- 系统与环境通道：屏幕感知（看界面）、系统事件感知（进程/文件/网络变化）、外设与网络设备感知（接入的设备状态）、语义感知（理解上下文意图）
- 机制价值：多通道感知让 Agent 从"只读用户文字"扩展到"能看、能听、能感知系统状态"，是 Agent 理解"我在什么环境、发生了什么"的基础
- 边界：感知通道越多，输入越杂，注入面与隐私成本也越大（关联 4.15 安全）——感知要按任务取用，不是越多越好

**本节即全章地图**
- 静态篇（4.4–4.10）：逐一深化结构维各零件——规划、行动（工具 / MCP / Skill）、记忆、知识（RAG）
- 动态篇（4.8，4.11–4.12）：看行为维如何落地与提质——ReAct 范式、思考质量（CoT）、输入控制（Prompt）
- 工程篇（4.13–4.18）：装配与量产——框架、多智能体、安全、评测、调试、推理服务
- 感知与反思没有独立小节不是遗漏：它们没有专属"机器"，其深化自然落在动态篇的"观察"与"判断"中（见 4.11 ReAct）


## 4.4 Planning 规划

> 本节深化五环节中的"规划"环节：任务执行前，Agent 如何把模糊目标变成可执行、可验证的步骤？

- Planning 是任务执行前的拆解环节：复杂目标被拆成可验证的子任务，每个子任务有明确的完成条件，便于逐步验证和推进
- 任务拆解让复杂目标转化为更容易验证的子任务
- 计划在生成后保持可变更，随执行结果和新信息动态调整
- 执行中发现前置条件不成立时，根据新信息调整计划或重新规划
- 规划的核心是把目标分解到位

**为什么拆解能降低风险**

- 子任务粒度小、完成条件明确，错误在局部就能被发现并纠正，不会一路累积到最终结果（与闭环"判断"步配合）
- 一次性规划到底依赖所有假设都成立；允许计划变更，环境反馈才能修正方向

- 注意误区："规划保证所有子任务并行完成"是错误说法——子任务之间存在依赖时必须按序执行，能并行的只是相互独立的部分

计划中的每个"行动"步都要调用工具——下一节看 Agent 如何获得执行能力。

## 4.5 工具调用与 Function Calling

> 本节深化"行动"环节：模型只输出文本，如何让参数精准地驱动真实工具？

### 从模型输出到工具执行

- 工具调用让 Agent 获得执行能力：模型依据工具描述选择工具并生成调用参数，外部执行层负责真正调用
- Function Calling（函数调用）协议：模型输出结构化的调用请求（函数名 + JSON 参数），外部执行层真正执行并把结果回传模型
- 这一"生成 → 执行 → 回传 → 继续生成"的接力，正是 4.1 中"决策者与执行者分工"的技术实现

### 工具描述与 Schema
```
{
  "name": "get_weather",
  "description": "查询中国城市天气，不支持海外",   ← 工具描述
  "parameters": {                                ← Schema
    "type": "object",
    "properties": {
      "city": { "type": "string" },
      "days": { "type": "integer", "minimum": 1, "maximum": 7 }
    },
    "required": ["city"]
  }
}
```
- 工具描述和 Schema 声明工具的用途、参数名称、参数类型和取值范围
- 工具 Schema 以 JSON 形式描述参数名称、类型和取值范围，模型据此生成合法参数
- 工具描述明确"何时使用"和"不能做什么"，降低错误工具选择和越权调用
- 生成后的参数需要校验类型和取值范围，防止非法参数进入执行层——模型可能生成"看似合理但越界"的参数，执行前校验是最后防线

### 失败处理

- 工具调用失败时分析失败原因，决定重试、换工具或终止
- 有副作用的操作（下单、发消息、写文件）避免无条件重试——重复执行可能造成重复业务
- 高频陷阱：工具返回错误信息时"默认成功或直接忽略"是错误做法——必须让模型看到错误并纳入下一步决策

**为什么 Schema 与错误回传如此重要**

- 模型对工具的全部认知来自描述文本，描述模糊等于让模型盲猜参数——工具描述就是"给模型看的 API 文档"
- 忽略错误等于切断闭环的反馈回路（4.3）：错误信息也是"观察"结果，必须进入"判断"

单一应用接三五个工具，直接写调用代码即可；当工具和应用的数量都增长，就需要统一协议——MCP。

## 4.6 MCP

> 本节继续深化"行动"环节：当工具与 AI 应用的数量都增长时，如何避免重复适配？本节回答三个问题——**MCP 的本质是什么、由哪几部分组成、如何落地实现**。

### 本质：把"需要能力的一方"与"提供能力的一方"解耦

- MCP（Model Context Protocol，模型上下文协议）不只是"工具调用标准"，本质是**把"谁需要能力"与"谁提供能力"拆成协议两端，用一套标准消息交换**，让二者无需知道对方的具体实现。"AI 应用 ↔ 外部能力" 之间的**通用插座**，一次封装处处可用。
- 封装化简：没有协议时，每个 AI 应用都要为每个工具单独写一遍适配代码——这就是 N×M 问题；有了协议，工具厂商只需让工具"说 MCP 语言"（实现一次），所有支持 MCP 的应用都能接入。


### 组成：三个角色，各司其职

MCP 用 Host / Client / Server 描述"谁决定要、谁去连、谁提供"：

| 角色 | 是什么 | 职责 |
|---|---|---|
| Host（宿主） | 用户直接使用的 AI 应用（Claude Desktop、Cursor） | 决定引入哪些能力、装配哪些 Server |
| Client（客户端连接器） | 宿主内部**与某个 Server 保持 1:1 连接**的组件 | 发起握手、发请求、把结果转回给 Host |
| Server（服务器） | 实际提供能力的程序（即第 7 章的 server.py，内部用 FastMCP） | 暴露能力、执行调用、返回结果 |

```
Host（AI 应用）─── 按 mcpServers 清单自动实例化 ───► 内含 N 个 Client
   ├─ Client#1 ──协议连接──► Server A（stdio / HTTP）───►Promitive1 |───►Tool1
   |                                               |               |───►Resource1
   |                                               |               |───►Prompt1
   |                                               |───►Promitive2
   |                                               |....(封装多个Promitive)
   ├─ Client#2 ──协议连接──► Server B
   └─ Client#3 ──协议连接──► Server C
```

| 关系 | 性质 | 谁发起 |
|---|---|---|
| Host ↔ Client | 组成 / 实例化（Client 住在 Host 里） | Host 按配置创建 |
| Client ↔ Server | 协议连接（stdio / HTTP） | Client 建立 |

- **高频易混点：Host ≠ Client**。Host 是整台"应用机器"；Client 只是 Host 里"负责连某一个 Server 的那条通道"
- 接入时配置里**只写 Servers、不写 Client**，因为那份配置是 **Host 的配置**，Client 是 Host 内部早已存在、要连就自动建立的通道，无需也不应声明

**三者如何连在一起**
- 关键：Host 与 Client 之间**不是"协议连接"，而是"包含 / 实例化"关系**——Client 是 Host 按需创建的子组件、就"住在"Host 里；真正发生协议连接的是 **Client ↔ Server**
- 装配流程：Host 读配置（`mcpServers` 清单）→ 为**每个** Server 实例化**一个** Client → 每个 Client 各自与它对应的那个 Server 建立**真正的协议连接**（stdio 拉起进程 / HTTP 访问）
- 星型拓扑：Host 是中心，内部挂 N 个 Client，每个 Client 各连 1 个 Server，多个 Server 互不干扰，所以"多接一个能力"= 多实例化一个 Client


### 三大原语（Primitive）：不只工具

"行动"不止工具一种，MCP 抽象出三类可接入能力——**这三类都由 Server 暴露**；接入一个 Server = 接入它暴露的全部原语。

**三类原语分别"由谁暴露、谁取用、怎么取用"**：

| 原语 | 谁暴露 | 功能 | 谁取用 | 协议方法 | 有无副作用 |
|---|---|---|---|---|---|
| Tools | Server | 模型调用去执行、有副作用的动作（查成绩、下单、写文件） | 模型按需选、去执行 | `tools/list` 发现、`tools/call` 调用 | 有（执行动作） |
| Resources | Server | 供应用读取的数据 / 上下文（文件内容、数据库记录） | 应用直接读取 | `resources/list`、`resources/read` | 无（只读） |
| Prompts | Server | 预置的可复用交互模板（固定话术模板） | 用户 / 客户端复用 | `prompts/list`、`prompts/get` | 无（模板） |

- 三者都无需改上层应用即可接入；区别在"给谁用、怎么用"——**Tool 让模型干活、Resource 给应用喂数据、Prompt 给用户/客户端固定话术**。


### 传输方式：本地与远程

消息跑在这两类传输上：

#### 本地传输

- **stdio**：Client 拉起 Server 进程，用标准输入 / 输出通信——本地工具，比赛场景（见 7.2 / 7.4）
**stdio 三流分工（协议与日志硬隔离）**

以 Server 进程为视角（Client 是拉起它的另一端），三个标准流各管一段：

| 流 | 方向 | 用途 | 是否协议 |
|---|---|---|---|
| stdin | Server ← 收 | Client 发来的请求 / 通知（JSON-RPC 进） | 协议 |
| stdout | Server → 发 | Server 回给 Client 的协议消息（JSON-RPC 出） | 协议 |
| stderr | Server → 发 | **日志、警告、错误等非协议文本**，给人 / 日志系统读 | 非协议 |

 - 完整链路：**stdin 进、stdout 出、stderr 旁路**，协议和日志被硬性分开；
 - 为什么必须隔离：Client 会把 stdout **逐字节当 JSON-RPC 解析**，一写日志进去，握手 / 调用全部错乱；
 - 这是 Unix 通用约定而非 MCP 特例：数据结果走 stdout、诊断信息走 stderr，`2> server.log` 即可单独落盘（见 7.7 排障）

- stdio 是默认模式：客户端配置只写 command / args，客户端负责"拉起"服务器进程（见 7.4）

#### 远程传输
- **HTTP + SSE（及后续 Streamable HTTP）**：Server 独立常驻，Client 经网络访问
- SSE 的本质：一次**不结束的 HTTP 响应**——Client 发一个 GET，Server 返回 `Content-Type: text/event-stream`，连接保持打开，Server 持续往响应体里写 `data:` / `event:` 帧；所以 SSE 就是 HTTP 的一部分，只是服务端能"主动、持续推数据"
- 方向性：SSE **只能服务端 → 客户端（单向）**；客户端 → 服务端仍走普通 HTTP 请求

**远程的两种形态（旧 → 新）**

- **HTTP+SSE（早期，双端点）**：收请求的 POST 端点 + 出响应的 SSE 端点分开，两个 URL、逻辑割裂，已被规范让位
- **Streamable HTTP（当前主流，单端点）**：一个端点同时承载两种通信——Client→Server 走普通 POST（请求-响应）；需要长任务 / 服务端主动时，同端点可返回 SSE 流，所以既能"一次请求"也能"持续收流"

**远程方向流总览**

| 方向 | 怎么做 | 说明 |
|---|---|---|
| Client → Server | HTTP POST 请求 | 请求-响应式，普通网络调用 |
| Server → Client | 同端点返回 SSE 流（流式） | 长任务回传进度 / 服务端主动推送 |

**HTTP 常见方法（小 tips）**

| 方法 | 语义 | 用途 | 会改数据？ |
|---|---|---|---|
| GET | 读取 / 获取 | 查数据、订阅流（SSE 用） | 否（安全 / 幂等） |
| POST | 提交 | 下单、发消息、MCP 调用（tools/list、tools/call） | 会 |
| PUT / PATCH | 更新 | 覆盖 / 局部修改 | 会 |
| DELETE | 删除 | 删资源 | 会 |

- 速记：**GET 只读、POST 提交、PATCH 改一部分、DELETE 删除**——GET 参数在 URL（可缓存 / 收藏），POST 参数在请求体（可有业务副作用）
- 对到 MCP 远程：**Client → Server 发调用用 POST**（提交 `tools/list` / `tools/call`）；**Server → Client 回推流用 GET**（建立 SSE）



与 stdio 的本质差异：

stdio 里 Client **拉起同机进程**；远程里 Server **独立常驻**、Client 用 URL 访问（可跨机、走公网）——**协议消息完全一样，变的只是"消息塞进哪个通道"**

选型判断：
本地 / 同机 → stdio；独立部署 / 跨机 / 常驻服务 → HTTP/SSE（Streamable HTTP）

一个 MCP 服务的完整生命周期（对应 7.3 的代码）：

1. **定义**：用 FastMCP 写工具函数，装饰器按函数签名（名称、类型注解、默认值）自动生成工具描述与 Schema（见 7.3）
2. **启动**：`mcp.run()` 拉起 Server、进入监听
3. **握手**：Client 发 `initialize`，Server 回应支持的能力与版本；Client 再发 `initialized` 通知——协商版本与技术栈
4. **发现**：Client 调 `tools/list`，Server 返回工具清单（名称、描述、参数 Schema）——即"服务启动时向客户端声明工具清单"
5. **调用**：Client 调 `tools/call`（工具名 + JSON 参数），Server 执行并返回结果
6. **反馈**：结果回传模型、纳入下一步决策——对齐 4.5 的"生成 → 执行 → 回传 → 继续生成"接力

- 工具描述 + Schema 是 Server 给模型的"说明书"，决定模型能否选对工具、生成合法参数（联动 4.5 的参数校验）
- 有状态的工具把数据写本地文件（常用 JSON），服务重启后重载（见 7.3）；接入配置后重启客户端重新发现工具，并实测调用 + 重启后数据完整

### 边界与注意

- 价值：标准化适配、一次实现处处复用、能力被封装在受控进程里形成**隔离**（授权与资源边界更清晰）
- 边界：工具少时直接调 API 更简单；MCP 解决"接口标准"，**不解决"能力质量"**——工具内部逻辑仍需自己写好
- 高危陷阱：异常输入应返回明确结果，**不能让异常导致服务进程退出**——服务崩溃会连带该 Server 上全部工具不可用（见 7.7 排障）

（从零实现一个 MCP 服务与接入客户端的完整代码见第 7 章）

MCP 统一了工具的"接口标准"，Skill 则把工具组合成"专业能力"——抽象层级再上一层。

## 4.7 Skill

> 本节收尾"行动"环节：有了工具，为什么还需要 Skill？答案——**工具是"零件"，Skill 是把零件按专家流程装好的"整机"**。

### 本质：固化成可复用黑盒

- Skill 是 Agent 预定义的专业能力模块，把一组工具和业务流程封装成可复用的高层能力；把"专家是怎么一步步干的"（触发 → 步骤序列 → 工具调用 → 产出口径）**固化成一段可复用流程**，用户只需给目标，不必自己编排
- 抽象层级高于单个底层 Tool：Tool 是"原子动作"，Skill 是"原子动作 + 编排顺序"的组合包
- 大部分 Skill 本质就是封装好的函数调用，智能来自工具的选择与组合

> 完整、可运行的 Skill 示例（把多个底层工具编排成"学生成绩分析"一个入口，并接入 Agent 循环由模型一键调用）见**第 7 章 §7.6「把流程封装成 Skill」**。

### 内部构成

把四件事打包在一起：

- **触发条件 / 意图**：什么时候该用——写成描述供模型识别该不该调它
- **步骤序列**：固定的执行顺序（业务流程）
- **工具调用 + 参数映射**：每步调哪个 Tool、用户目标怎么映射成该 Tool 的参数
- **产出口径**：返回什么格式的结果

### 运行机制：Skill 怎么被调用

- Skill 本身**以"工具"的形式暴露**给模型（有自己的名称 + 描述 + 参数 Schema），模型把 Skill 当作一个大工具去选、去调——入口机制与 Tool 一致（联动 4.5 / 4.6）
- 差别在"体内"：Tool 被调用即执行原子操作；**Skill 被调用后，内部再依次去调用若干底层 Tool**，拼成完整方案
- 所以 Skill = "模型看得到的大工具 + 内部编排若干小工具"——复杂度被封装在 Skill 内部，模型无需感知细节

### Tool / Skill / Workflow 三层对比

| 层级 | 是什么 | 谁来组合 | 灵活度 |
|---|---|---|---|
| Tool（工具） | 单个原子操作（如"搜索"） | 模型每轮现场选择 | 最灵活，但每轮都要决策 |
| Skill（技能） | 工具 + 业务流程的封装包 | 预先编排、可复用；模型选入口，内部走固定路径 | 折中 |
| Workflow（工作流） | 固定路径的流程编排 | 人预先画死（见 4.13） | 最确定，但最不灵活 |

- 递进本质：**越往上，"设计时"预定的逻辑越多、"运行时"临场决策越少**，换来确定性、可复用、更可靠，代价是灵活度下降
- Skill 的定位：把"反复要做、形态稳定"的路径预编译；若任务形态差异很大，过度固化的 Skill 反而限制模型发挥

"行动"环节到此拆完，接下来看五环节中的"记忆"。

## 4.8 Prompt 工程

> 本节深化"输入控制"：每轮循环的质量上限由输入决定，Prompt 是 Agent 唯一不变的"控制面"。

### 本质：只有输入可调，输入决定上限

- Prompt 是发给模型的指令，质量直接影响生成结果
- 机制：LLM 是无状态自回归生成器，没有隐藏"配置文件"——它对任务的全部认知都来自上下文（4.2）。所以**输入质量 = 输出质量上限**，同一套模型换一种 Prompt 表现天差地别（Garbage in, garbage out）
- 因此 Prompt 工程是 Agent 里**唯一不换模型、可反复调优的杠杆**，把"期望行为"翻译成"模型能听懂且会照做的语言"

### Prompt 的构成：给什么 + 怎么给

- **系统提示词**：设定角色、行为规则、边界——定义模型的"人格"与红线，通常放最前、每轮不变
- **用户提示词**：具体任务指令——说明完成什么、以什么格式输出，是每轮变化的"任务卡片"
- **示例（few-shot）**：给输入输出示范，让模型"照样子做"
- 指令要明确、具体，避免模糊表述

**分层机制的重要**

- 对模型而言，系统消息和用户消息都是"上下文"，没有真正"绝对指令"，只有**铺垫顺序 + 一致性**带来的隐性优先级；所以工程上做分层：系统提示词放**稳定层**（身份/规则），用户提示词放**可变层**（当次任务），外部内容放**更低信任层**，分层让"边界"可控（呼应 4.15 安全）

**结构化 Prompt 示例**

```
system: 你是成绩查询助手。规则：查询必须调用工具、只按工具结果回答、查不到就如实说明。
user:   查询"李明"的成绩并判断是否通过，以 JSON 输出 {name, score, passed}
示例:   user "查询王雪" → assistant {"name":"王雪","score":58,"passed":false}
```


### 常用技术

- **Few-shot 少样本提示**：给若干输入输出示例，让模型模仿规律完成新任务——适合"规则强、难用语言描述"的任务；示例质量决定上限
- **思维链 CoT**：引导分步推理再给出答案，适合数学、逻辑、规划（详见 4.12）——把中间计算显式写进上下文
- **输出格式化**：要求 JSON 等结构化格式，便于程序解析——Agent 的输出常被代码消费，结构化是刚需（对齐 4.5 的 Schema 思维）
- **角色设定**：指定专家角色，约束回答风格与范围——借"角色"锚定语言风格与知识边界
- **温度参数**：控制输出随机性——低温度适确定性任务，高温度适创意生成（机制见 1.3）——注意：温度是**采样参数而非 Prompt 内容**，但同属"控制面"的另一半

### 注意事项

- 提示词中的内容都可能被模型当作指令——用户输入和外部内容需要做注入防护
- 外部检索内容注入提示词前，应与系统指令做隔离：RAG 检索回来的内容也是"不可信文本"，不能直接获得指令权限（详见 4.15）
- 复杂任务在提示词中说明执行步骤，降低模型遗漏环节的概率


至此，单 Agent 的"控制面"讲完；下一节看五环节中的"记忆"

## 4.9 记忆

> 本节深化"记忆"环节：上下文窗口有限（4.2），Agent 如何记住窗口装不下的信息？

### 短期记忆与长期记忆

- 记忆模块保存后续决策可能需要的历史信息
- 对话中的临时信息放在短期记忆中，随上下文窗口轮换——窗口就是短期记忆的物理载体，装满了旧内容就被挤出
- 需要长期保留的信息写入外部持久化存储，形成长期记忆
- 长期记忆可跨会话使用，保存范围大于有限的上下文窗口

### 长期记忆的设计问题

- 设计需考虑：哪些信息值得保存、信息是否过期、谁有授权访问、检索时如何控制相关性
- 检索出过期信息时，为记忆增加时间来源或有效性判断（否则 Agent 可能基于过期状态做决策）
- 记忆写入与检索都要有访问控制（记忆里可能存有敏感信息）

**为什么记忆不是"全存"**

- 存得越多，检索噪声越大、成本越高；记忆的价值在"需要时找得到"，不在"什么都存"
- 短期记忆 ≈ 窗口内的对话历史（免费但易失、容量小）；长期记忆 ≈ 窗口外的外部存储（持久但需检索与维护）——记忆模块的本质是把窗口装不下的信息外置

记忆存的是"经历"（对话与操作历史）；Agent 还需要"知识"（事实与文档），通过RAG实现。

## 4.10 RAG 与向量检索

> 本节回答三个连环问题：模型训练后内部知识就固定了，如何让它回答"没学过"的问题？（为什么需要 RAG）RAG 到底是一套怎样的"开卷"机制？（怎么运作）更进一步，"Agent 型 RAG"究竟是 RAG 还是 Agent？（边界澄清，高频易混）——它是静态篇"知识"这个零件的外挂，承接 4.9 的记忆。

### RAG 是什么

- RAG（Retrieval-Augmented Generation，检索增强生成）= 先"查资料"再"作答"：生成之前先用检索从外部知识库找到相关片段，把片段拼进上下文，模型再基于这些资料生成答案
- 定位：RAG 是一类**增强生成的技术方案**，本身不是 Agent。普通 RAG 是一条固定管线；只有当"检索"这一步被交给一个能自主决策的 Agent 去执行时，才升级为"Agent 型 RAG"（见本节点末尾）
- 与记忆的分工：记忆存"经历"（对话与操作历史），RAG 补"知识"（事实与文档）——一个面向自己的历史，一个面向外部的资料

### 解决什么问题

- 模型知识停留在训练截止日期；内部制度、最新文档、私有数据等模型并没有学过
- RAG 在生成前把外部知识注入上下文——相当于"开卷考试"：不往脑子里塞书，考前把资料发给你
- 与微调的对比（高频）：RAG 在推理时检索外部知识并加入上下文，新增知识无需修改基础模型参数——知识更新只需更新知识库，成本远低于重新微调；微调则用数据更新模型参数
- 一句话选择依据：缺的是"没学过的知识" → 用 RAG；要"学会某种风格/行为" → 用微调（RAG 与微调对照见 ch06 §6.4）

### 完整流程：离线建库 + 在线检索

RAG 分两个阶段：**离线建库只做一次**（准备知识），**在线检索每次查询都做**（取用知识）。

- 第一阶段 · 离线建库（把资料变成可检索的向量，做一次）：
  1. 文档切块，把长文档拆成适合检索的文本片段
  2. 用 Embedding 模型把片段编码为向量，存入向量库（常见：Milvus、Chroma、FAISS）
- 第二阶段 · 在线检索（每次提问都执行）：
  3. 用户提问时把问题编码为向量，在向量库中检索相似片段
  4. 把检索结果拼入 Prompt 上下文，交给模型生成回答

### 关键机制：切块 / 检索 / 重排 / 混合

检索效果几乎由"知识库构建 + 检索策略"决定，这些机制共同决定"能捞回什么、捞回的质量如何"：

- 切块大小是两难：检索的最小单位是"块"，块太小语义不完整，块太大命中不精准，常用几百到上千 Token 的块——本质是语义完整性与命中精度的折中
- 切块重叠：相邻块共享边界内容，给边界内容上"双保险"，防止语义被切断
- 向量检索（粗排）：从百万块中快速捞回候选（快但粗）
- 重排 Rerank（精排）：用更重的模型对少量候选二次排序（慢但准）——粗排 + 精排的分工，提升答案质量
- 混合检索：结合向量相似度与关键词匹配，兼顾语义和精确词命中
- 查询改写：把口语化问题改写为规范表述，提升相关性
- 知识库更新：新增文档需重新切块并写入向量库，定期维护
- 检索结果也是"不可信文本"：注入上下文前应与系统指令隔离，否则可能被当作新指令执行（详见 4.15）

### 原理与边界

- Embedding 把文本映射到向量空间，语义相近的文本向量距离更近
- 向量相似度衡量当前表示下的语义接近程度
- 高频陷阱（边界）：高向量相似度只说明两个文本在当前表示中更接近，单独不能证明事实内容一致——检索结果只是"候选资料"，不是"已验证事实"
- 因此 RAG 的答案是"检索相关"而非"必然正确"，可靠性仍取决于知识库质量与筛选，不能把检索命中当作事实成立

### Agent 型 RAG（是 RAG 还是 Agent？）

- 一句话定位（高频易混）：Agent 型 RAG **本质仍是 RAG**，是 RAG 家族的一种**架构变体**，而不是"带 RAG 的普通 Agent"
- 机制：把"检索"这一步工具化、决策化——检索不再"每问必做一次"，而是被当作一个可反复调用的动作，纳入闭环决策（检索 → 看结果 → 不够 → 换查询再来）
- 与普通 RAG 的区别：普通 RAG 每问固定检索一次、一次到底；Agent 型 RAG 根据当前情况**自主决定**是否再次检索、换查询或取消检索
- 为什么叫"Agent 型"：因为"要不要检索、怎么检索、何时停止"的自主权交给了 Agent 式的推理循环，而不是因为它本身是"一个带 RAG 的 Agent"——它仍是"检索增强生成"，只是检索过程更智能

**RAG → Agent 型 RAG → 完整 Agent 的递进（自主权从"检索"扩展到"任务"）**

| 形态 | 检索的自主权 | 目标 |
|---|---|---|
| 普通 RAG | 固定：每问检索一次 | 由检索增强地回答 |
| Agent 型 RAG | 自主：可多次、可换查询、可停止 | 把检索流程本身变得可决策 |
| 完整 Agent | 检索只是众多工具之一 | 完成更复杂的任务，不限于问答 |


## 4.11 ReAct

> 动态篇开篇：执行闭环（4.3）最经典的实现范式——ReAct，让"思考"与"行动"交替进行。

<Mermaid chart="flowchart TD; A[思考 Thought] --> B[行动 Action 调用工具]; B --> C[观察 Observation 读结果]; C --> A; C --> D{信息充足?}; D -- 否 --> A; D -- 是 --> E[输出最终结果]" caption="ReAct 循环：思考→行动→观察，边想边做" />

- ReAct 把推理和行动交织进行，循环流程为思考、行动、观察，再进入下一轮思考，直到任务完成
- 思考：确定下一步做什么，例如搜索什么资料
- 行动：调用工具，例如执行搜索
- 观察：读取工具返回的结果，例如找到几篇文章
- Observation 承接行动后的外部结果，用于指导后续推理和行动
- 信息充足后停止循环，输出最终结果

**ReAct 与执行闭环的对应**：思考 ≈ 计划 + 判断、行动 = 行动、观察 = 观察——ReAct 就是把 4.3 的抽象闭环落成具体的循环实现。

**为什么"边想边做"优于"想完再做"**

- 一次性规划到底依赖所有假设成立；ReAct 每轮根据观察修正方向，错误只存活一轮
- 观察为何关键：它把环境反馈（包括工具错误）注入下一轮思考——切断它，循环就退化为盲跑
- 与 CoT 的区别（高频）：CoT 的"思考"不一定会触发外部工具调用，ReAct 把思考与工具行动交织在一起（对比见 4.12）

ReAct 循环的质量取决于每轮"思考"的质量，下一节的 CoT 提升单轮推理的可靠性。

## 4.12 CoT 思维链

> 动态篇第二环：让循环中每一轮"思考"更可靠。

- CoT（Chain-of-Thought，思维链）是引导模型"先逐步推理、再给出答案"的提示技术，能显著提升数学、逻辑、常识推理类问题的表现
- 大模型直接回答复杂问题时容易"跳步出错"，把推理过程显式写出来可降低错误率
- 核心：在 Prompt 中要求模型输出中间推理步骤，再给出最终答案
- 为什么有效（机制）：模型逐 Token 自回归生成（4.2），没有隐藏草稿纸——"一步一步想"相当于把中间计算状态显式写进上下文，模型可以"看着"前面算的结果继续算，减少粗心错误与幻觉

三种常用形式：

- Few-shot CoT：在示例中展示"推理步骤 + 答案"的完整过程，让模型模仿
- Zero-shot CoT：不给示例，只加一句"Let's think step by step"（让我们一步一步地思考）即可触发分步推理
- CoT-SC（Self-Consistency，自洽性）：同一问题让模型多次独立推理，对多个答案投票取多数，进一步提升正确率

适用与局限：

- 适合：需要多步计算的数学题、需要链条式推理的逻辑题、需要逐步拆解的规划类任务
- 不适合：简单事实问答（直接回答更快、更省 Token）
- 局限：推理步骤本身也可能出错，CoT 只是降低出错概率，并不保证正确

无论是 CoT 还是 ReAct，每轮循环的输入都是 Prompt——最后一环看如何控制输入质量。

## 4.13 开发框架与工作流

> 工程篇开篇：从零手写 Agent 可行，但生产级 Agent 通常基于成熟框架开发，以复用工具集成、记忆、编排与部署能力。

### Workflow 与 Agent 的分界（高频）

- Workflow 是固定流程编排，执行路径预设，适合确定性任务
- Agent 是动态决策，根据执行结果调整路径，适合开放任务
- 选择依据：任务确定且重复 → Workflow（可控、可预期）；任务开放多变 → Agent（灵活但需护栏）
- 工具数量少时直接调用 API 更简单，工具数量多时使用统一协议更高效（呼应 4.6）

## 4.14 多智能体协作

> 工程篇第二环：什么时候值得拆成多个 Agent？代价是什么？

### 收益

- 多 Agent 系统让多个专业 Agent 分工协作，例如研究、写作、审核分别由不同 Agent 承担，各角色专注自身领域
- 角色分工和专业化提升整体能力
- 深化（为什么专业化有效）：每个 Agent 的上下文窗口有限（4.2），专注单一角色意味着上下文只装该角色的指令、工具与经验，减少无关信息稀释

### 代价

- 协作引入通信、重复工作和冲突开销
- 高频陷阱：增加 Agent 数量不一定提高任务质量，但协调成本一定随数量增长——不是"人越多越好"
- 协调机制包括：共享必要状态、明确角色职责、结果汇总或仲裁、任务分配

### 典型流程

- 典型流程为研究、编码、审查、测试，反馈修改后交付——每个环节的"反馈修改"本身就是一次小闭环

### 智能体编排与路由（平台级调度）

多智能体不仅要"会协作"，还要被"组织起来可调度"——这是编排与路由解决的问题：

- **智能体编排**：定义多个智能体之间的调用顺序与依赖（做图编排时可用 LangGraph 这类图结构，呼应 4.13），形成稳定的执行流程
- **智能体路由**：按任务类型、复杂度、可用资源，决定把任务交给哪个智能体承接，或拆分成多个智能体并行/接力
- 与多智能体协作的分工：协作讲"智能体之间怎么配合"，编排与路由讲"平台如何调度、分发这些智能体"——一个是角色间关系，一个是平台侧调度
- 平台价值：把"选谁来做、按什么顺序做"从每次临时决策，变成可配置、可复用的调度策略，系统更稳定、可扩展

Agent 数量越多、权限越大，出事的破坏面越大——安全随之而来。

## 4.15 安全

> 工程篇第三环：Agent 能执行实际操作，安全控制随之而来。三大风险：提示注入、越权工具调用、不可逆操作。

### 提示注入

- 提示注入可能来自用户直接输入，也可能隐藏在网页、文档等外部内容中——外部内容携带的指令同样有效
- 为什么注入有效（机制）：模型无法从原理上区分"指令"与"数据"，所有进入上下文的文本话语权相同——外部内容一旦进入上下文，就获得了与系统指令同等的"说话资格"
- 这正是 4.8 要求"外部内容与系统指令隔离"的原因：隔离不能消除注入，但能降低其权限

### 防护手段

- 最小权限原则：Agent 只获得任务所需的最小能力——即使注入成功，能动的范围也有限
- 明确接口和审计记录降低自动化执行风险；可审计工具接口记录操作过程，便于追溯
- 高风险动作前加入人工确认，在不可逆或敏感操作前增加控制点
- 关闭不需要的网络服务可减少系统攻击面

**运行时沙箱**：

- 安全不仅靠"权限给得少"，还要靠"运行环境隔离"——把 Agent 的执行限制在受控沙箱内，即使被注入、越权，也出不了沙箱
- 机制：智能体行为识别（对工具调用序列做合法性检查）+ 运行时沙箱（限制文件、网络、命令的访问范围，超界即拦截）
- 与最小权限的关系：最小权限定"能做什么"，沙箱定"在哪里做、做到哪一步算越界"——两者一个收权、一个划界，互补
- 边界：沙箱不是万能的，仍需配合审计与人工确认处理"合法权限内的恶意意图"

**USEC 安全体系（国产平台落地）**：

- USEC 是统信 UOS 的安全体系，把权限精细化管控、数据安全与系统稳定收进一套统一框架——上面讲的最小权限、沙箱、审计、数据不出域，在国产平台上被组织成体系化能力
- 对应国产生态的"自主可控"要求：安全不只是补丁式防护，而是从内核权限到应用运行的体系化防线（联动 ch02 文件权限、ch05 国产硬件自主可控）
- 与具体 Agent 安全手段的关系：Agent 安全手段（4.15 前文）是"通用方法"，USEC 是"这些方法在国产操作系统上的成体系落地"

安全管的是"别出事"，评测管的是"干得好不好"——怎么客观衡量？

## 4.16 Agent 评测

> 工程篇第四环：Agent 不是"能跑就行"，怎么客观衡量好坏？——先定指标，再选方法。

### 评测指标

- 任务成功率：任务是否按预期完成
- 工具选择准确率：是否选对了工具
- 平均调用次数或成本：执行是否高效
- 安全违规率：是否触发了越权或危险操作
- 执行稳定性：多次执行结果是否一致
- 高频陷阱：答案正确但调用大量无关工具，说明执行效率和工具选择质量仍需优化——"结果对"不等于"过程好"

**冗余推理与效率**：

- 多一次无效的大模型推理，就多一份算力与延迟成本——"工具直达执行路径"（确定该调工具时直接调用，不再绕一轮推理）是省算力的关键手段
- 机制：能确定的动作直接执行（如读取、解析、合并这类明确操作），把推理留给真正需要决策的环节；避免"每个小动作都问一遍模型"
- 对应用的价值：端侧设备尤其看重，直接决定响应速度与耗电

- 为什么过程指标不可省：Agent 的结果可能"碰对"（运气路径），且无关调用消耗成本、增加延迟、放大不确定性——过程指标衡量的是"可复现的可靠能力"

### 评测方法

- 自动评测：比对最终答案，检查工具调用序列是否合理
- 自动评估还可检查越权调用和安全违规
- 人工评测：评估任务完成度、过程合理性、交互体验
- 评测需要覆盖不同难度的任务集合，保证结果稳定

### 指标与方法的配合

- 自动评测管"可计算的"（答案对错、调用序列、违规计数），人工评测管"难量化的"（过程合理性、交互体验）
- 稳定性指标要求同一任务跑多次——对应自动评测的可重复执行

评测发现"分数不达标"，接下来定位问题出在哪一环——调试与排查。

## 4.17 调试与故障排查

> 工程篇第五环：按症状对照排查方向，日志是主要手段。

### 常见故障与排查方向

- 工具调用失败：检查工具描述与 Schema 是否准确，参数是否合法，工具是否可用
- 模型输出乱答：检查 Prompt 是否清晰，检索结果是否注入正确，采样参数是否合理
- 上下文溢出：单次对话内容超过上下文窗口（4.2），需要压缩历史或清理无关内容
- 死循环：Agent 反复执行相同动作，需要设置最大迭代次数和 Token 预算限制
- 检索不到答案：检查知识库内容是否覆盖、切块与检索参数是否合理（4.10）
- 幻觉输出：检索结果与回答不对应，需要约束模型只基于检索内容回答

### 排查手段

- 日志记录每一步的思考、工具调用和结果，是定位故障的主要手段——日志相当于把闭环的每一轮显式落盘
- 调试时逐步执行，观察每一步输入输出，定位出错环节
- Agent 进入死循环或浪费 Token 时，设置最大迭代次数和 Token 预算限制（兜底止损）
- 故障记录保留时间、操作和结果，有助于复现问题、审计过程和重复试错

问题修复后，Agent 要部署上线长期运行——最后一环是模型调用与推理服务。

## 4.18 模型调用与推理服务

> 工程篇收官：Agent 的大脑从哪来？本地还是云端？7 步把前文所有零件装配成完整应用。

### 调用方式

- API 调用：通过 HTTP 接口向推理服务发送请求，传入模型名、消息和参数，返回生成结果
- 本地调用：加载模型到本地内存，直接调用模型接口生成
- 两者区别在于模型运行位置，调用逻辑一致——数据敏感 / 离线场景选本地，快速起步 / 弹性伸缩选 API

### 推理服务

- Ollama 提供简单易用的本地模型部署和 API 接口
- vLLM 提供高性能推理服务，支持高并发和连续批处理
- 推理服务暴露 OpenAI 兼容接口，应用通过标准接口切换不同后端（换模型不用改代码）
- 本地模型部署需要考虑显存容量、量化级别和并发请求数（KV Cache 是显存大头，见 4.2）
- 模型推理参数包括温度、最大生成长度、Top-p 等，通过请求参数传入

**统一运行时与混合路由（平台化部署）**：

- 统一运行时（llama.cpp / ONNXRuntime / OpenVINO）：把不同推理引擎抽象成统一执行层，上层只面对一套接口，不用关心底层是哪个引擎在跑
- 统一 API 网关（DeepSeek / Kimi / GLM / QWen / GPT / Claude / 自定义）：屏蔽各家模型差异，对外一个接口，可随时切换或混用
- 混合路由引擎：按任务在端侧模型 / 云侧模型 / 私有化部署模型之间自动选择——数据敏感走端侧或私有化，重计算走云侧，兼顾"数据不出域"与"算力弹性"（呼应 4.18 本地 vs API 的取舍）
- 价值：把"模型选型"从一次定死变成"运行时可路由"，系统更灵活、可扩展

**AI SDK：能力的标准化出口**

- 平台把语音、视觉、文本、知识库、模型管理等 AI 能力封装成统一 SDK 接口，开发者无需理解底层细节即可快速集成
- 解决什么问题：每家企业都从零对接语音/视觉/知识库成本高、重复造轮子；SDK 提供"开箱即用"的统一入口，基于现有系统快速构建 AI 应用
- 与工具/MCP 的关系：SDK 侧重"给开发者调用的 AI 能力封装"，MCP 侧重"工具接口互通标准"——前者是能力出口，后者是工具互联协议

### 本地 Agent 的受控边界

- 本地 Agent 在受控边界内使用本地数据和工具——数据不出域 + 权限受控，是本地化部署的核心价值

### 应用构建流程（全章装配线）

1. 明确任务需求，确定模型选型
2. 部署模型或接入 API
3. 构建知识库，导入文档并建立索引（4.10）
4. 接入工具和系统能力（4.5–4.7）
5. 设计 Prompt 和 Agent 流程（4.8，4.11–4.12）
6. 运行调试，验证任务完成效果（4.16–4.17）
7. 排查错误，优化迭代

### 任务完成效果验证

- 用测试集验证任务正确率，检查工具调用是否合理
- 评估指标包括任务成功率、工具选择准确率、调用成本、安全违规率（4.16）
- 验证结果不达标时，从 Prompt、检索、工具参数、模型选型逐项排查

## 4.19 核心概念速览

按"起点 → 零件 → 循环 → 工程"收束全章：

- **起点**：模型生成文本，Agent 执行任务；LLM 出决策，执行层干活
- **大脑**：上下文窗口定记忆容量，Token 定计量单位，逐 Token 自回归生成是 CoT 的根源
- **零件**：Planning 拆目标，Tool 给执行能力（Schema 保证参数正确），MCP 统一工具接口，Skill 封装专业流程，Memory 存经历，RAG 补知识
- **循环**：五环节是零件清单，闭环是主循环；ReAct 是闭环的经典实现，观察结果驱动下一步决策；CoT 提升思考质量，Prompt 控制输入质量
- **工程**：框架管组装，Workflow 管确定性流程，Multi-Agent 管分工协作，安全管底线，评测管质量，调试管定位，推理服务管运行
- **一句话主线**：把只会生成文本的 LLM，装上骨架（闭环）、四肢（工具）、硬盘（记忆）、外脑（RAG）与护栏（安全 + 评测），就是 Agent
