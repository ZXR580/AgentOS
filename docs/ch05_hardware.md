## 5.1 国产计算平台

> 本节解决：国产 CPU 有哪些路线、为何分多种指令集、指令集如何决定程序能否运行。

### 国产 CPU 路线

| 厂商 | 产品系列 | 指令集架构 |
|---|---|---|
| 龙芯 | 龙芯 3A 系列 | LoongArch |
| 飞腾 | 飞腾系列 | ARM |
| 华为 | 鲲鹏系列 | ARM |
| 兆芯 | 开先、开胜系列 | x86 |
| 海光 | 海光系列 | x86 |
| 申威 | 申威系列 | SW64 |

- 指令集体系主要分 x86、ARM、RISC-V、LoongArch
- 为什么国产 CPU 分多种指令集：这是"兼容主流生态（x86/ARM，迁移成本低）"与"完全自主（LoongArch/SW64）"两条路线的取舍，兼顾生态可用性与自主可控
- x86 生态兼容性最好，应用迁移成本低——因为 x86 积累了海量现成二进制软件，兼容 x86 即可直接运行
- ARM 以低功耗高性能著称，服务器和移动端广泛应用（华为鲲鹏、飞腾基于 ARM，属"授权 + 自研核"路线）
- RISC-V 开源免费，生态仍在发展
- 指令集 vs 微架构：指令集是"接口规范"（规定指令长什么样），微架构是"具体实现"（如何执行）；同一指令集可有多种微架构实现

### 指令集与兼容性

- ISA 定义处理器能理解的机器指令、寄存器等基本接口
- 不同 ISA 的机器指令编码不同
- 同一份 x86-64 二进制程序复制到 ARM64 系统后无法运行，核心原因是机器指令集面向不同 ISA
- 跨架构运行需要目标架构构建或重新编译
- 为什么 x86 程序不能直接跑在 ARM 上：CPU 只认自己指令集的二进制，指令编码不同 → 必须重新编译（呼应 5.2 兼容性层次）

指令集决定了"程序能不能跑"，接下来分层看清兼容性的全貌——下一节讲兼容性层次。

## 5.2 兼容性层次

> 本节解决：应用跨平台/跨架构迁移时，从底层到上层要检查哪些兼容性。

兼容性问题需要分层看待，从底层到上层依次为：

| 层次 | 是什么 | 不兼容的后果 | 层次 |
|---|---|---|---|
| ISA 指令集架构 | 机器指令、寄存器的接口定义 | 不同 ISA 指令编码不同，x86 二进制拷到 ARM64 无法运行，需重新编译 | 硬件层 |
| API 应用程序接口 | 源码层面的调用约定 | 决定源码能否重新编译通过 | 软硬交界 |
| ABI 应用二进制接口 | 已编译二进制与运行库、系统接口的约定 | 决定已编译程序能否直接运行 | 软硬交界 |
| 运行库与依赖软件 | 共享库版本与架构 | 缺共享库 = 运行时依赖适配不完整，启动报错 | 软件层 |
| 操作系统接口 / 驱动 / 外设 | 系统调用、设备驱动、外设支持 | 缺驱动设备不可识别；识别 ≠ 功能与稳定性已验证 | 软硬结合 |
| 启动机制 | 服务如何拉起 | 启动方式 / 依赖服务变化需一并验证 | 系统层 |

关键判断（必考）：

- API 兼容 ≠ ABI 兼容：API 兼容只保证源码能重新编译，已编译二进制能否运行由 ABI 决定；API 兼容不自动保证 ABI 兼容
- 动态链接程序能否运行受共享库架构和 ABI 兼容性影响；应用启动报缺共享库属于运行时依赖层问题
- 应用能启动 ≠ 整体兼容：需验证完整技术栈组合与关键业务路径，单看组件能启动不够

迁移检查流程（配合 ch03 3.3）：

1. 盘点应用清单与依赖，识别迁移范围与潜在问题
2. 搭建目标架构环境
3. 按上表逐层做兼容性验证
4. 回归测试确认未破坏既有功能

- 跨 CPU 架构迁移重点解决：机器指令（ISA）、目标架构构建、运行库、驱动四类问题

兼容解决"能不能跑"，异构解决"用什么跑最快"——下一节讲异构计算。

## 5.3 异构计算

> 本节解决：为什么需要多种计算单元，它们各自擅长什么、如何协同。

### 计算单元定位

| 类型 | 定位 | 特点 |
|---|---|---|
| CPU | 通用计算，擅长复杂逻辑与任务调度 | 灵活，并行计算效率有限 |
| GPU | 大规模并行计算 | 并行强、生态成熟 |
| NPU | 神经网络专用加速 | 低功耗，适合本地运行 |
| TPU | Google 专用 AI 处理器 | 针对 AI 和 Google 体系优化 |
| ASIC | 专用集成电路 | 效率高，成本高且不灵活 |
| FPGA | 可重构硬件 | 可重新配置，开发复杂 |

为什么需要异构：不同负载对算力要求不同，串行逻辑 CPU 强、海量并行 GPU 强、特定神经网络 NPU 最强，单一单元无法兼顾所有负载
- GPU 适合大量并行度高、计算密集的任务
- NPU 面向神经网络等特定负载做专用加速
- CPU 为压缩单线程延迟而设计：高主频 + 乱序执行 + 分支预测 + 深层缓存

异构计算强调 CPU 与不同加速单元按任务特点协同配合
协同方式：CPU 负责调度与串行部分，GPU/NPU 负责并行计算，通过 PCIe/NVLink 等互连通信
GPU 峰值算力高不意味着任意程序在 GPU 上都一定比在 CPU 上运行得快，串行逻辑仍是 CPU 优势。
算力指标 TFLOPS 表示每秒万亿次浮点运算

异构里的主力加速器是 GPU——下一节深入 GPU 架构与 CUDA 编程。

## 5.4 GPU 架构与 CUDA 编程

> 本节解决：GPU 到底是什么、由什么组成；海量核心为何让显存带宽成为第二瓶颈；CUDA 如何组织线程、数据如何流动、多个 Kernel 如何接力——形成"组织 → 执行 → 存放 → 传递"的完整闭环。

**GPU 是什么**：Graphics Processing Unit，图形处理器。最初为渲染而生——对百万像素做相同运算，天然并行；于是走了与 CPU 相反的路线：把控制电路压到最低，省下的晶体管全部复制成海量简单核心，靠"同时干活"堆出高吞吐。

### GPU 硬件结构设计

组成层级（由整体到局部）：

```
GPU 芯片 —— 多个 SM + 显存控制器（经它与显存交换数据）
 └─ SM 流式多处理器 —— GPU 核心计算单元，调度执行大量线程
     ├─ CUDA Core ×多个 —— 通用计算单元，最小的"笨核"
     ├─ Tensor Core —— 专用加速单元，把矩阵乘加做成硬件电路
     ├─ Warp 调度器 —— 硬件电路：挑一个就绪的 warp，取一条指令广播给整束（SIMT 的指挥官）
     └─ shared memory（SRAM）—— 就近供数，块内共享
```


- 同构并行：大量简单计算单元 + SIMT 架构，适合"大量相同操作"的任务（逐像素渲染、矩阵乘）；CPU 用少量复杂核心擅长串行逻辑——两者是分工而非替代
- SIMT（Single Instruction Multiple Threads，单指令多线程）是"堆核"成立的关键：warp 内 32 个线程共用一套取指译码电路、同一时刻执行相同指令，控制电路省下的晶体管全部换成计算单元。
- Warp 线程束是基本调度单位：32 个线程为一组，SM 以 warp 为粒度调度发射——warp 是线程的"组"（组织形式），发射它的 warp 调度器是硬件warp调度器。
warp=32Thread：控制电路摊销想要大（一套电路带的线程越多越省）、分支发散惩罚想要小（组越大越容易走岔）——32 是折中；且 32 线程 × 4 字节恰好一个 128 字节访存事务（合并访问的物理基础），2 的幂还便于用一个 32 位掩码标记每线程的存活状态
- CUDA Core 是通用计算单元：可编程的算术执行单元，什么运算都能做——但只管"算"，取指译码归 warp 调度器，与 CPU 那种自带控制+缓存的完整核心不是一回事
- Tensor Core 是专用加速单元：一条指令直接驱动乘加器阵列完成整个矩阵乘加（D = A×B + C），省去通用核逐条指令拼算的开销——"用专用换算力密度"，是深度学习训练的关键（深度学习 90% 以上的计算正是矩阵乘加）
- 工艺节点影响性能与功耗平衡，7nm 是高端 AI GPU 的标志性节点——层级能堆多密，最终受制于工艺

海量核心同时开工，数据供给立刻成为新瓶颈——这正是显存与带宽问题的由来。

### 显存与带宽

**显存的地位**：GPU 体系里的"主存"。GPU 内部是一条存储层级金字塔（越近越快、越小、越贵）：

```
寄存器             每线程私有，就在执行单元旁，Thread独享               最快；每线程限量
shared memory     块内共享，SM 内部（SRAM），Block内共享       快；每 SM 几十 KB
L2 缓存            全卡共享，兜底热点数据                      中；几~几十 MB
────────────────────────────────────────────
显存（全局内存）    GPU 的"主存"，DRAM 颗粒，全卡所哟线程共享    慢（几百周期）；几~几十 GB、TB/s 级带宽     
────────────────────────────────────────────
PCIe（Peripheral Component Interconnect Express，高速串行点对点总线） 
────────────────────────────────────────────
主机内存           CPU 的内存  最慢一跳；但容量可以很大                                      
```

- 与 CPU 体系的角色对应：CPU 内存 ↔ 显存、CPU 缓存 ↔ shared memory/L2、CPU 寄存器 ↔ GPU 寄存器
- 寄存器和 shared memory 只在 Kernel 执行期间存在——想活过 Kernel 边界的数据必须落显存（下文数据流的根基）

显存看两个维度：

- 显存容量决定能装载的模型参数和数据量，若容量不够模型放不下，只能多卡切分
- 显存带宽决定数据读写速率，单位 GB/s 或 TB/s；为什么大模型要 HBM：数据搬运（带宽）常是瓶颈，带宽越高算力越能发挥

两类显存是"快"与"省"的取舍：

| 显存 | 如何实现 | 特点 | 用途 |
|---|---|---|---|
| GDDR | 传统平面布线的 DRAM 颗粒 | 带宽较低、成本低 | 消费级显卡 |
| HBM 高带宽内存 | 多层 DRAM 堆叠 + TSV 互连，2.5D 封装与 GPU 直连 | 带宽可达数 TB/s、低功耗 | 数据中心 GPU |

DRAM 是"一个电容存 1 位"的大容量存储颗粒（GDDR/HBM 都是 DRAM 家族，区别不在怎么存、在怎么连线）；TSV 是打通叠层芯片的垂直硅通孔（上千条并行短通道）；2.5D 封装是经中介层转接板把 GPU 与显存并排密集互连。

- HBM 为什么快：堆叠缩短互连距离、TSV 提供大量并行通道、2.5D 封装与 GPU 直连——三个手段都在提高"单位时间搬进芯片的数据量"；GDDR 不堆叠、靠 PCB 走线，只能拉高频率硬顶，带宽天花板低、功耗高

硬件决定上限，程序决定能兑现多少，CUDA 就是"把任务拆成海量线程喂给核心"的方法论。

### CUDA 编程模型

- CUDA 是 NVIDIA 2006 年推出的并行计算平台和编程模型，GPU 编程事实标准
- CUDA C/C++ = C/C++ 语法 + 少量 GPU 扩展关键字
```
vecAdd.cu（源码，磁盘上）
   ↓ nvcc 编译（关键：一个编译器拆两份！）
┌─────────────────────────┬──────────────────────────┐
│ CPU 机器码（x86/ARM…）    │ GPU 机器码（PTX→SASS）     │
│ main()、cudaMemcpy 调用  │ vecAdd 函数体               │
│ 装进可执行文件 .exe       │ 也装进同一个 .exe 里        │
└───────────┬─────────────┴────────────┬─────────────┘
            ↓ 运行时                      ↓ 启动 Kernel 时
        CPU 取指执行                随启动命令传给 GPU
        （读 CPU 指令缓存）         → 装进 GPU 显存
                                     → SM 的 warp 调度器取指
                                       广播给整束执行
```
- Kernel 由 CPU 端调用启动，GPU 并行计算；启动即异步：`<<<>>>` 发出后 CPU 代码继续往下跑，Kernel 在 GPU 上后台执行
**Kernel**：被并行执行的那段代码——`__global__` 的函数
- 标了 __global__ 的函数归 GPU，其余的 main、辅助函数归 CPU
- CUDA编程的心智模型：执行范式是 SPMD（单程序多数据），所以写代码时站在单个线程的视角——线程执行同一份代码、不写 for 循环（循环被"拆成人海"）、靠索引各领各的数据、结果写进显存（Kernel 无返回值，显存里被改写的数据就是它的"返回"）

```c
__global__ void vecAdd(float* a, float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x; 
         └ 前面有几个block ×每块线程数 ┘   └ 块内偏移 ┘  
    if (i < n) 
        c[i] = a[i] + b[i];                  // 运算定义
}
vecAdd<<<160, 256>>>(a, b, c, n);  // 160 块 × 256 线程 = 40960 线程同时进入
vecAdd<<<320, 128>>>(a, b, c, n);
```
| 内置变量 | 是什么	| 谁填的 | 例（<<<160, 256>>>）|
| --- | --- | --- | --- |
| blockIdx.x | 所在的 Block 在 Grid 里的编号 | 硬件自动填 | 0 ~ 159 |
| threadIdx.x | 在 Block 内的编号 | 硬件自动填	| 0 ~ 255 |
| blockDim.x | 每块多少线程（维度） | 启动参数 | 256 |
| gridDim.x	 | Grid共多少块（维度）| 启动参数 |	160 |

**三级组织与硬件映射**。线程组织分三级：Grid、Block、Thread
```
vecAdd 这个 Kernel（一份代码）
 │
 ├─ 第一次启动 <<<160, 256>>>  → Grid #1（40960 个线程：160 Block × 256）
 |                                   Grid（一次 Kernel，自定义线程数：4 Block × 256 Thread = 1024 线程，处理 1024 个元素）
                                        |
                                        ├─ Block 0（自定义线程数量，推荐为32倍数，因为会被切成多个warp）──── 整块进驻 SM#0（一个 SM 可同时驻留多个块）
                                        │    ├─ Warp 0 = 块内线程 0–31    ┐
                                        │    ├─ Warp 1 = 块内线程 32–63   │ 每束 32 Thread
                                        │    ├─ …                         │ 同一时刻整束只执行同一条指令
                                        │    └─ Warp 7 = 块内线程 224–255 ┘
                                        ├─ Block 1 ──── 进驻 SM#0
                                        ├─ Block 2 ──── 进驻 SM#1
                                        └─ Block 3 ──── 进驻 SM#1
 ├─ 第二次启动 <<<320, 128>>>  → Grid #2（新的一批人，跑的还是同一份代码）
 └─ ……

```
| 编程单位 | 硬件落点 | 说明 |
|---|---|---|
| Thread 线程 | 在 CUDA Core 上执行 | 最小编程单位 |
| Block 线程块 | 整块分配到一个 SM | 块内线程共享 shared memory、可同步 |
| Grid 网格 | 分布到全卡所有 SM | 启动一次 Kernel 的全部线程 |

- 为什么恰好三级：Block 是**协作边界**（shared memory 与同步电路都在 SM 内，整块落进同一个 SM 才能走"近道"）；块间不许同步、不保证执行顺序——换来可扩展性：块数远多于 SM 数也能排队补位，同一份程序不改一行就能跑在不同规模的卡上；跨块的全局依赖靠"拆成两个 Kernel"解决（Kernel 边界 = 天然全局同步点）

** 
- Grid/Block/Thread 是**逻辑组织**（程序员定的分工与协作边界）
- Warp 是**执行组织**（硬件定的调度粒度，固定 32、按块内编号连续切分、永不跨块）


**模板要求与自定义**：

- 块数与每块线程数是**启动参数，程序员任意定**（4×256 只是示例）——总线程数 ≈ 数据规模；块数 ≥ SM 数量，否则一堆 SM 空转
- 每块线程数上限 1024，且**建议 32 的倍数**：切不整会出"残束"（100 线程 = 3 个整束 + 4 人残束，28 个通道空转）
- 一个 SM 驻留几个 Block 由**硬件上限**决定：驻留块数（16/32）、驻留 warp 数（48/64）、寄存器总量、shared memory 总量四项同时满足才算住得下——任一资源耗尽即到顶；多余的块排队补位，这正是不依赖具体 SM 数量的可扩展性来源

五条性能规则，每条背后是一个硬件事实：

- warp divergence 线程束发散：同一 warp 内线程执行不同分支时需串行，严重降低并行效率——根源是 SIMT：32 线程必须同一时刻执行相同指令，分支只能排队走
- shared memory 共享内存：块内线程共享，延迟远低于全局显存——它就在 SM 内部，离计算单元最近
- 内存合并访问：相邻线程访问相邻内存地址时合并为少量事务，提升带宽利用率——带宽是稀缺资源（承上节：喂不饱核心）
- 原子操作：确保多线程对同一地址的并发操作无数据竞争——海量线程并发写同一地址时的秩序保障
- CUDA Stream：管理操作并发执行，不同 Stream 中的操作可并行——让"计算"与"数据搬运"重叠，提高核心利用率

### 数据流与 Kernel 间协作

> 组织（Grid/Block/Thread）→ 执行（Warp/SIMT）→ 存放（存储层级）之后，最后一环是**传递**：数据从哪进、算完去哪、多个 Kernel 如何接力。

**入口**：一切原始数据的正门是主机内存 → PCIe → 显存（cudaMalloc 开显存、cudaMemcpy 搬数据、再启动 Kernel）。PCIe 带宽比显存带宽低几十倍——所以用 Stream 让"搬运下一批"与"计算当前批"重叠。Kernel 链之间不必回 CPU：Kernel1 写进显存的中间结果就是 Kernel2 的输入，在 GPU 上接力。

**算完去哪**：warp 的计算结果先落各线程**寄存器**，之后三选一：

| 去向 | 何时用 | 代价 |
|---|---|---|
| 留在寄存器继续算 | 后续步骤马上要用 | 零，最快路径 |
| 写 shared memory | 块内其他线程要用 | 低（SM 内部） |
| 写显存（store） | 最终结果 / 要活过 Kernel 边界 | 高（几百周期 + 耗带宽） |

- 没有自动回传：GPU 不会"算完自动送回"，不写 store 结果即丢

**判断数据住哪层（三问决策树）**：

- 谁用？（只有本线程 → 寄存器；块内共用 → shared memory；跨块 / 下个 Kernel / CPU → 必须显存）
 × 
- 用几次？（一次就丢 → 寄存器路过即可；反复用几十次 → 值得搬进 shared 复用）
 ×
- 要活过 Kernel 边界吗？（要 → 无论多小都必须落显存）。
- 代码里用声明写定：局部变量 → 寄存器、`__shared__` → 共享内存、`cudaMalloc`/`__device__` → 显存

**多轮计算三模式**（按数据的生存周期分层）：

- 步与步之间：留在寄存器滚——起点 load 一次、终点 store 一次，中间全在寄存器
- 块内协作：经 shared memory 中转，如矩阵乘把子块搬进 shared，一次显存搬运换几十次近距复用
- 跨块 / 跨 Kernel：必须绕显存，CUDA 没有 block 间通信原语（块调度完全自由，硬件无法保证对方已写完，干脆禁止——换来可扩展性）；块间交换数据的唯一路径是 A store → 显存 → B load

**Kernel 间接力：三样契约**（Kernel1 的输出如何成为 Kernel2 的输入）：

- 同一个**指针**：两次启动传同一个显存地址——没有"传递"，只有"共屋檐"；GPU 没有"输出注册表"，Kernel1 甚至不知道 Kernel2 的存在
- 同一**流（Stream）的顺序**：同流 Kernel 严格按发射顺序排队——Kernel1 的所有块全部完工、数据落显存后，Kernel2 才被允许启动（"Kernel 边界 = 全局同步点"的机制实体）；不同 Stream 可并行，但依赖关系要自己用 event 管
- 同一套**索引约定**：指针定位缓冲区在哪、索引算术定位格位归谁、流顺序保证"写完才读"——深度学习的层间接力、KV Cache 常驻显存被逐层读写（ch01），底层都是这一套

Conclusion：**CPU 经 PCIe 把数据送进显存 → Kernel 按索引把任务拆给海量线程 → warp 锁步执行、结果落寄存器 → 按三问分层下沉（寄存器滚 / shared 复用 / 显存交接）→ 下一个 Kernel 凭同一指针 + 流顺序接力 → 最终结果经 PCIe 取回主机。**

### 生态库

- cuBLAS 基础线性代数库，矩阵乘法等运算的底层基石
- cuDNN 深度学习加速库，针对卷积、池化、归一化优化
- TensorRT 高性能推理优化器，通过层融合、INT8/FP16 精度校准加速推理
- NCCL 多 GPU 集合通信库，提供 AllReduce、Broadcast 等原语
- PyTorch 等框架的分布式训练以集合通信库为底层后端

## 5.6 大模型训练集群

> 本节解决：大模型单卡装不下/太慢时，如何用多卡并行，通信为什么是关键。

### 并行策略与通信

| 策略 | 切分方式 | 通信特征 | 适用场景 |
|---|---|---|---|
| 数据并行 | 每卡完整模型，不同数据批次 | 梯度同步通信量大 | 模型能装入单卡 |
| 模型并行 | 模型层切分到不同 GPU | 通信中等 | 超大模型 |
| 流水线并行 | 按层分段处理 | 段间传递开销小 | 深度模型 |
| 张量并行 | 单层参数切分到多 GPU | 通信频率极高 | 大模型、MoE |

- 通信带宽不足影响所有并行策略——为什么：并行要频繁交换梯度或中间结果，通信慢了整体就被拖住
- 高速互联方案：InfiniBand 400G 以上为高性能首选，RoCE 100G/200G 为性价比方案
- GPU 间通信依赖高速互联网络
- 大模型训练以混合精度为主，权重 FP32 存储、FP16 计算
- 硬件视角：并行策略与 ch01 1.4 模型工程一致，此处侧重集群互联与带宽

多卡并行让功耗与发热飙升——下一节讲散热配套（液冷）。

## 5.7 液冷与散热技术

> 本节解决：高功耗芯片为什么必须液冷，液冷系统如何组成、如何运维。

### 为什么需要液冷

- 为什么高功耗芯片必须液冷：风冷散热能力有物理极限（约数百瓦），GPU 功耗达 500W 以上后风冷压不住，必须靠液冷带走热量
- 液冷支持 500W 以上高功耗芯片，散热能力优于风冷
- 液冷降低 PUE、支持更高密度部署、降低噪音
- 液冷优势在于提升持续算力释放，避免高功耗 GPU 过热
- 液冷系统仍需定期检查维护

### 液冷分类

| 分类 | 原理 | 特点 |
|---|---|---|
| 直接接触式 | 冷却液直接与芯片接触 | 热路径短、散热效率高，冷却液必须绝缘 |
| 间接接触式 | 冷却液流经冷板内部，经冷板导热 | 安全性高、兼容性好，使用常规冷却液 |

- 冷板液冷属于间接接触式液冷
- 冷板与芯片顶盖接触，通过热传导带走热量
- 常用冷却介质为去离子水或乙二醇水溶液
- 冷却液要求导热系数高、电导率低，普通自来水含杂质离子，适合直接使用
- 乙二醇可降低冰点防冻，导热系数低于纯水

### 系统组成

- 冷板液冷系统分三层：外部冷源、CDU 冷却液分配单元、冷板
- CDU 负责冷却液分配与热量转移，内含循环泵、板式换热器、过滤器、膨胀罐、控制系统
- 工作回路为循环泵、分液器、快接头、冷板、回流
- 循环泵驱动冷却液流动，选型看流量、扬程、可靠性
- 快速接头支持在线维护，要求无滴漏
- 气液分离器排出气泡，漏液检测绳和传感器用于早期泄漏侦测

### 运维与故障

- 首次启动或长停机重启，先查液位和管路密封性并充分排气
- 长停机时排空冷却液并干燥管路
- 漏液故障：关断对应阀门、定位、更换密封件
- 冷板堵塞导致效率下降：反向冲洗、更换冷板、加强过滤
- 泵故障：切换备用泵、排气、更换泵
- 冷却液中断或大量气泡聚集，最直接风险是热击穿
- 导热硅脂涂覆均匀最佳，过厚增加热阻
- 冷板安装按对角线顺序逐步均匀拧紧
